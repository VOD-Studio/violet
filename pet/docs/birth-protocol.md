# 出生承诺—揭示协议（R-02）

#518 的评审输出。**本协议没有经过独立安全评审，通过评审前不得宣称“正式可验证发行”或“公平”。** 本文说明协议做什么、不能证明什么、密钥如何轮换，以及交给评审者的检查清单。

## 参与者与目标

- 服务端（签发方）持有签名密钥；客户端是领取宠物的用户；验证者是任何持有证书与签发方公钥集的人。
- 目标：给定一张证书，验证者能确认**这个出生结果确实由这些输入决定**，并且服务端在看到客户端随机材料之前就已经固定了自己的随机材料。

## 步骤

1. **固定上下文**：世界、发行者、签名密钥标识（`kid`）、请求标识、领取资格摘要、规则版本、签发时间。
2. **承诺**：服务端生成本次专用的 `server_seed`，公布 `commitment = SHA-256(上下文, server_seed)`，并对承诺签名（承诺收据）。
3. **接受客户端随机**：客户端提交 `client_seed`；服务端把它**持久固定**，再签发接受收据，签名覆盖上下文、承诺与 `client_seed`。
4. **揭示与派生**：服务端公布 `server_seed`，按 `derive_birth` 派生身份、稀有度、物种与基因，装配证书。
5. **验证**（核心里的纯函数 `verify`）：选钥并检查有效窗口与撤销 → 验承诺收据 → 核对承诺与揭示一致 → 验接受收据 → 重算出生结果并比对。

## 验证的判定

`valid`、`unsupported_rules`、`bad_encoding`、`unknown_key`、`key_not_valid`、`key_revoked`、`commit_signature`、`commitment_mismatch`、`accept_signature`、`result_mismatch`。每一类篡改都有测试对应：改服务端随机、改客户端随机、改签名、改稀有度、改世界、改规则版本、改签发时间、换签发密钥、冒用他人公钥。

## 它能证明什么

- 证书里的结果与输入一一对应，任何人可重算。
- 服务端承诺 `server_seed` 在先，客户端随机在后，服务端**事后不能因为看到了客户端随机而更换种子**（测试：换种子后承诺不匹配）。
- 服务端确实在承诺之后才接受了该 `client_seed`（接受收据的签名）。
- 证书不含登录凭据、邮箱或原始活动记录（测试：证书不含账号字段）。

## 它不能证明什么

这些边界必须随协议一起对外说明：

1. **不能证明服务方没有选择性拒绝请求。** 服务端可以丢弃它不喜欢的领取。
2. **不能证明不存在多账号偏差。** 同一个人用多个账号重复领取，协议无从发现；只能靠账号层面的限制，且限制不是协议的一部分。
3. **服务端仍可在承诺前预先挑选种子。** 它在承诺时不知道客户端随机，所以结果对它不可预知，但它可以在更早的阶段无限次生成候选种子再挑一个承诺；客户端随机的作用是让这种挑选对结果无效。
4. **揭示前中止是可能的。** 服务端在接受 `client_seed` 后已能算出结果，若不喜欢可以不揭示。缓解：在同一事务里完成“接受并生成证书”并持久化，使诚实实现没有可中止的窗口；客户端保留两张收据，作为服务端扣留结果的证据。这是证据而不是预防。
5. **`issued_at` 由签发方自报。** 它受签名保护，但无法防止签发方在密钥被盗后伪造早于撤销时间的签发时间。撤销被盗密钥时应取**最早可能的泄露时间**作为 `revoked_at`；要真正防止倒填需要透明日志，不在本期范围。
6. **签发方与验证者拿到的公钥集必须可信。** 本协议不解决公钥分发。

## 隐私

- 公开凭据只含世界、发行者、`kid`、请求标识、资格摘要、规则版本、签发时间、两份随机材料与出生结果。
- `request_id` 由服务端随机生成，**不得嵌入账号标识**；资格摘要是对主体加盐哈希得到的不透明值，只用于防止重复提交，外部无法反推账号。
- 账号与证书的归属记录是**私有记录**，与公开证书分开存放，公开页面只读公开部分。

## 密钥管理（已实现）

- 证书标明 `kid`；验证方持有一组 `IssuerKey`（`kid`、公钥、生效时间、结束时间、撤销时间）。
- **轮换**：旧钥设置结束时间，新钥设置生效时间；窗口内签发的旧证书在新密钥集下**仍然有效**（AC-19，测试覆盖）。过了窗口再用旧钥签发会被判 `key_not_valid`。
- **撤销**：自撤销时间起（含）签发的证书无效，之前的证书不受影响（测试覆盖边界）。
- 密钥集缺少证书所标 `kid` 时返回 `unknown_key`，公钥格式错误时返回 `bad_encoding`，都不会 panic。
- 尚未实现：密钥集的发布与获取方式（建议随服务公开 JWKS 风格的端点）、私钥的存放与访问控制、轮换的运维流程。

## 重试与恢复语义（待 #525 实现，AC-03）

出生请求在服务端是一条持久记录，状态依次为：已承诺 → 已接受 → 已揭示，**每一步写入后才对外可见**：

- `server_seed` 在承诺时即写入存储（静态加密），因此服务重启不会重抽；
- 同一请求标识的重试返回已有状态对应的对象，**不能**在接受之后更换 `client_seed`，也不能改变上下文；
- 同一请求标识换了参数返回冲突，沿用存储契约里的“请求标识复用”判定。

## 交给独立评审者的检查清单

- [ ] 承诺、两份收据与证书的签名域是否相互隔离，是否存在跨协议重放（域分隔标签是否足够）。
- [ ] 编码是否无歧义（长度前缀拼接）、字段顺序是否固定。
- [ ] `server_seed` 的生成、存放与销毁；随机源质量；静态加密密钥管理。
- [ ] 上述“不能证明什么”六条是否准确、是否有遗漏的攻击面。
- [ ] 密钥轮换与撤销在运维上的可操作性，以及被盗后的恢复流程。
- [ ] `request_id`、资格摘要是否可能反推账号。
- [ ] 速率限制与账号层面的反刷策略是否应纳入协议规范。
