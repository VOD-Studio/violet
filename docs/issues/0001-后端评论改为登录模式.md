# Issue-0001：后端评论双轨认证 + 提交者可见 pending

## Parent

PRD-0001（`docs/prd/0001-锚点批注评论.md`）

## What to build

建立评论的**双轨认证模型**——底部自由评论轨保留匿名访客模式（昵称 + 邮箱），选区批注轨强制登录。同时让评论列表返回 `approved` 联合「当前登录会话用户自己的 `pending`」，使登录提交者能在审核通过前看到自己刚提交的评论（带「审批中」语境）。

端到端行为：
- **匿名评论（底部自由轨）**：`POST /comments` 不带 `anchor` 时，匿名可用（沿用现有 `author_name/email` 模式）；返回 201。
- **批注（选区批注轨）**：`POST /comments` 带 `anchor` 时，强制登录；未登录返回 401。
- **登录用户**：作者信息（`author_name` / `avatar_url`）从会话用户记录填充，请求体传这些字段也以会话为准（防伪造）。
- `GET /posts/{postId}/comments`：返回该文章所有 `approved` 评论，**外加**当前登录会话用户自己的 `pending` 评论（匿名 viewer 不看到任何 pending；他人 pending/spam/deleted 不可见）。
- `CommentDTO` 新增 `status` 字段，让前端能为登录提交者渲染「审批中」徽章。
- 限流沿用 `CommentRateLimit`（3/min/IP），不变。

本 issue **不**做 anchor 字段本身（Issue-0003 落地 schema，但本 issue 先在 handler 层实现「带 anchor 时强制登录」的校验逻辑——通过请求体是否有 `anchor` 键判断，anchor 的实际存储和校验在 Issue-0003）、不做 pictures 接线（Issue-0003）、不碰前端 UI（Issue-0002）。

**实现注**：本 issue 与 Issue-0003 在 anchor 上有交接面。最简分工：Issue-0001 只在 handler 层加「请求体含 `anchor` 非空对象 → 校验登录」的早返；anchor 的五元组结构校验、DB schema、DTO 序列化都在 Issue-0003。两边都在 handler 层操作 `anchor` 字段，注意 Issue-0003 不要重复实现登录校验。
