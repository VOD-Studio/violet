# Issue-0005：OTel 跨服务 trace context 传播

## Parent

PRD：`../../prd/0007-mimo-music-phase-3.md`（user stories 6、7；Implementation Decisions - OTel 跨服务传播）

## What to build

让 mimo-music 能从入站请求的 W3C `traceparent` 头提取 trace context，使外部调用方（mimo-blog 或任何 OTel-instrumented client）发起的请求在 mimo-music 侧产生的 span 成为调用方 span 的子 span，形成一条完整链路。同时把 trace_id 与日志串联，从一条日志能跳到对应 trace。

server 侧：HTTP server 加 `otelhttp.NewMiddleware`（或等价的 handler middleware），从 `traceparent` / `tracestate` 头提取 context，给每个入站请求创建 server span。现有 `otel_handler.go` 注入日志的 trace_id 逻辑保持兼容——提取出的 span context 同样能被日志 handler 拿到。

worker 侧：Asynq 任务加 trace context 传播。Asynq 任务入队时若携带 trace context（payload 或 header），worker 处理时提取并创建任务 span，使异步任务链路与触发它的请求串联。若 Asynq 当前不支持，至少保证 worker 的任务 span 有独立 trace，不污染主链路。

本切片不含 mimo-blog 侧改动（迁移不纳入本批 issues）。端到端传播验证用纯 mimo-music 侧可复现的方式：起一个带 `otelhttp.NewTransport` 的 HTTP client 注入 traceparent 打到 mimo-music server，用 tracetest 断言 server 产生的 span 是 client span 的子 span（共享 trace_id、parent span_id 正确）。

## Acceptance criteria

- [x] mimo-music HTTP server 加 otelhttp middleware，从 `traceparent` 头提取 context 并创建 server span
- [x] 提取出的 span context 的 trace_id 能被现有 `otel_handler.go` 注入到日志 record
- [x] Asynq worker 任务经 TraceMiddleware 创建独立任务 span（命名 `asynq <tasktype>`）
- [x] `trace_id` 与日志串联：从一条请求日志能拿到 trace_id 跳到对应 trace（日志 handler 已有逻辑，本切片确认在新链路下仍生效）
- [x] tracetest 端到端验证：带 traceparent 的 client 请求 → server span 与 client 同 trace（共享 trace_id，沿 parent 链可追溯）
- [x] 无 traceparent 头的请求仍正常工作，server 自行起一条新 trace
- [x] worker 入口的任务 span 有合理命名（如 `asynq <tasktype>`），不泄漏内部细节
- [x] 所有导出符号有 godoc 注释

## 实施备注

**worker trace 降级**：当前 TraceMiddleware 只为每个任务起独立根 span（定时任务无上游 HTTP 请求，不尝试从 asynq payload 提取 traceparent）。这是 spec 允许的兜底（"至少保证 worker 的任务 span 有独立 trace，不污染主链路"）。完整的"异步任务链路与触发请求串联"需要 Asynq 支持 context 传播（任务入队时注入、worker 提取），留给后续迭代——当前 mimo-music 的定时任务场景下，任务无上游请求触发，独立根 span 已足够让任务在 trace UI 可见并与日志串联。

## Blocked by

- Issue-0004（OTel 真实 exporter 接入）。跨服务传播的前提是 exporter 能真正导出 span，否则只能验进程内 span 无法验链路串联。
