# 自定义表情：私有默认、引用式收藏、独立聚合

聊天/评论/推文新增用户自传表情能力。核心决定：自定义表情**默认私有**（只有上传者可选用，他人在内容中能看到渲染结果但不能直接选用），需**右键收藏**（引用式，非拷贝）才能获得选用权；数据模型是**独立于现有 `domain/emoji` 的新聚合**，不复用后台管理员维护的系统表情目录；渲染解析改为**按表情 ID**而非按名称（系统表情继续按名称，两套 token 互不冲突）。

## Considered Options

- **可见性**：私有默认 + 收藏获取 vs 上传即全站公开可选。后者会让「收藏」退化为纯书签（不再是获得能力的动作），且新表情的曝光面从「被主动收藏」扩大到「全站表情选择器人人可选」，风险面更大。
- **数据模型**：新聚合 vs 给现有 `EmojiGroup`/`Emoji` 加 `ownerID`。后者能直接复用现成的渲染/选择器代码，但会把「后台管理员维护目录」（`emoji:manage-group` 等权限、B 站重拉取）和「用户自服务上传/删除/收藏」两种互不相关的生命周期糅进同一聚合。
- **名称解析**：全局唯一名 vs 按 ID 解析。现状 `FindByNames` 本就是全站按名查找、不分组不分用户；放开用户自建后如果仍按名称唯一约束，热门词会被第一个上传者「抢注」，后来者持续撞车；按 ID 解析从根上消灭重名/改名/删除引发的渲染漂移。
- **收藏语义**：引用 vs 拷贝。拷贝会让已被收藏、已扩散的违规表情副本在原始上传被下架后仍然留存，直接抵消「管理员删一次、全部收藏者同步失效」的事后审核策略。

## Consequences

- 评论 (`comment_container.go`)、推文 (`tweet_container.go`) 现有两份结构相同的 `EmojiLookup` 适配器，加上聊天新增的按 ID 解析逻辑会形成第三份重复；需要收敛到一个共享 application 层实现（接口仍按域拆分，实现合一）。
- 新增一个全站挂载的 `ContextMenu` UI 原语（`shared/ui/base/context-menu.tsx`），按右键目标类型决定是否弹出、弹什么；系统表情与非表情内容的右键行为不变。
- 表情下架（管理员或上传者自行删除）级联影响全部收藏者；历史内容中的表情按现有 `EmojiText` 的「未匹配 `[name]` 保持原文」兜底逻辑自然降级，不需要新增特殊处理代码。
