# 已读回执由阅读位置水位推导，不建逐条回执表

Status: accepted（2026-08-31）

## 背景

聊天需要发送者视角的已读回执（「我发出的消息对方读没读」）。接收侧已有阅读位置（`chat_read_positions`：每成员每会话一条水位记录，含最后读到的消息 ID 与标记时间），支撑未读角标。回执的数据来源有两条路线：复用水位推导，或新建逐条逐成员的已读回执表（WhatsApp 式）。

## 决策

已读回执从阅读位置水位推导，不建独立回执存储：

- 成员是否读过消息 M = 其水位不早于 M（比较口径与未读计数完全一致：创建时间在前，或同时刻但消息 ID 不大于水位 ID，见 `MemberReadState.Covers`）。
- 私聊中自己发送的每条消息带「已读/未读」状态；房间中按聚合计数显示「N 人已读」（不计发送者本人），名单经 `GET /conversations/{id}/messages/{messageId}/readers` 按需查询，仅发送者可见。
- 阅读位置推进时向其他有效成员广播 `read.advanced` 事件，复用聊天事件表与 SSE 断线补发；重复标记同一位置不广播。
- 回执对称可见，不提供关闭开关。

## 理由

1. 会话内消息按时间线性排列，水位语义天然覆盖「读到哪」；逐条回执表在聊天场景表达不出水位表达不了的状态。
2. 零 schema 变更：回执、未读角标、断线补发共用同一份数据与比较口径，不会出现两套已读语义漂移。
3. 回执表成本随 消息数 × 成员数 增长，而水位是每成员每会话一行。

## 代价

- 无法表达「读了后面的消息但没读前面的」这类非连续已读——水位模型下该状态不存在，产品上也无此需求。
- 将来若真要逐条粒度（如单条消息的精确已读时间线），需要新建回执表并回填，迁移成本真实存在。

## 否决的替代方案

- **逐条逐成员回执表**：表达力超出水位模型的部分在聊天场景无对应产品语义，存储与写入放大明显，否决。
- **已读事件只存内存、不落事件表**：断线重连后回执丢失，与事件契约（ADR-0011 的补发约定）冲突，否决。
- **「已送达」回执**：需要客户端 ack 管线，复杂度与收益不成比例，本期不做。
