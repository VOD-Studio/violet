# 看板画布使用自写拖拽控制器，包内保留引擎无关的接缝

`@violetjs/kanban` 的画布拖拽由自写的指针控制器实现，不依赖 dnd-kit 等拖拽库。包内把「输入如何变成移动」抽成**拖拽控制器**接缝：指针输入进入，产出一次移动（见 `CONTEXT.md`「看板组件」），默认实现是自写指针控制器，更换实现不影响包的公开接口。键盘移动按离散的列与位置进行，不经过这个接缝，由看板直接提交同样的移动。这推翻了访谈阶段「不自己造拖拽引擎」的默认。

依据是原型里两个引擎在同一块缩放画布上的对比（Chromium 桌面，脚本化验证：跨阶段指针拖拽、自动排序列拒绝手动排序、键盘拿起移动放下、51% 缩放下的落点），两者都能完成，差别在适配成本。dnd-kit 在 transform 定位的缩放画布里需要补的东西：

- 默认测量忽略节点自身的 transform，起始矩形算偏约 650px，需改用 `getBoundingClientRect`。
- 拖拽中被拖节点必须不动，其余卡片的实时让位要另写。
- `DragOverlay` 里的内容要手动乘以缩放。
- 没有画布边缘自动平移。
- SSR 水合需给 `DndContext` 固定 id。
- 键盘需自写 `coordinateGetter`。

补完这些之后，库提供的只剩传感器和碰撞检测，自写指针控制器即可覆盖同样的行为，并且落点换算、自动平移、让位动画与画布视口共用同一套坐标。

否决的方案：继续使用 dnd-kit 并叠加上述适配——适配层与库的内部测量耦合，升级时容易失效；完全不设接缝、把自写实现写死在画布里——日后更换控制器实现就得改画布本身。

代价是无障碍语义、触屏、多指针都由包自己负责，而原型只验证了 Chromium 桌面的指针与键盘。触屏拖拽、双指缩放、读屏播报和多指针必须在真机与真实读屏上验证，列为实现阶段的验收项。「移到…」菜单是拖拽的单指针替代（WCAG 2.2 的 2.5.7），不依赖控制器实现。
