# PRD: 全站通知系统（notifications）

## Problem Statement

violet 的通知能力是断裂的。领域事件（评论、友链申请、订阅抓取失败、登录异常……）已经在 EventBus 上流动，审计 subscriber 也在记录"发生了什么"，但用户（admin 和普通用户）**无法及时得知需要自己关注的事**：

- 订阅连续失败 5 次（`consecutive_failures=5`），订阅所有者毫不知情，只能手动进后台列表才看到 `last_error`。
- 友链申请提交后，站长只能手动刷新后台的 pending 计数才知道有新申请。
- 评论审核通过后，评论作者收不到反馈。
- 异常登录、角色变更等安全事件，用户无感知。

根因：**EventBus 上缺少"通知"这一消费者**。审计（append-only 记录）和通知（targeted + readable state）是两个正交关注点，当前只有前者，没有后者。

手动触发类操作（如订阅抓取的"立即拉取"）同步阻塞 HTTP 线程，用户必须盯在界面等结果——这也源于没有"提交后异步执行 + 结果通知"的基础设施。

## Solution

新增独立 bounded context **`notification`**，作为 EventBus 的第二个 subscriber（与审计 subscriber 平行）。通知是写时扇出（fan-out-on-write）的领域模型：事件发生 → subscriber 计算接收者 → 给每个接收者写一行通知 → SSE 实时推送。

### 核心设计

- **传输层**：SSE 实时推送（复用 code-runner 已验证的 SSE 模式），前端 EventSource 自动重连 + 断连补发兜底。轮询仅作 fallback。
- **数据模型**：非规范化单表 `notifications`（`user_id` + `source_type` 枚举 + `source_id` + `payload` JSONB + `read_at`）。每个接收者一行，零 JOIN 查询。
- **扇出策略**：写时扇出。violet 的通知源绝大多数是 1:1（评论→作者、订阅失败→订阅主），最大 fan-out 是通知管理员（当前 2-3 人）。已否决 follow 关系，无 celebrity problem。
- **已读状态**：服务端 `read_at` 字段，跨设备同步。
- **保留策略**：全保留。violet 用户量级（几百到几千）× 低频事件 = 一年几万行，PostgreSQL 无压力。可选定期清理（清理 job 属 Out of Scope）。
- **扩展点**：多实例水平扩展时用 Redis pub/sub 广播（当前单实例不做）；邮件渠道预留接口（当前不实现）。

### 交付分期

| 期 | 内容 | 验收 |
|---|---|---|
| P1 | 后端通知领域 + EventBus subscriber + API + SSE 推送 + 前端通知铃铛（未读计数 + 列表 + 标记已读） | 订阅抓取失败、友链申请、评论审核通过三类通知端到端跑通 |
| P2 | 订阅抓取"立即拉取"改异步（POST 立即返回 → goroutine 后台跑 FetchNow → 结果通知） | 手动触发不再阻塞 UI |
| P3 | 通知偏好（用户可关闭某类通知）+ 聚合（高频通知合并，如"X 评论了你的文章"多条合并为"X 等 3 人评论了你的文章"） | 用户可控通知噪音 |

本 PRD 聚焦 P1 + P2，P3 记录决策待后续。

## User Stories

1. 作为登录用户，我要在站点任意页面看到通知铃铛，未读数实时反映（SSE 推送）。
2. 作为登录用户，点击铃铛打开通知列表，看到最新通知（谁/什么事件/何时/关联资源），分页加载更早的。
3. 作为登录用户，点击单条通知或"全部已读"后，未读数实时减少，已读状态跨设备同步。
4. 作为订阅所有者，当我的订阅连续抓取失败时，收到通知告知失败原因，无需手动查后台。
5. 作为站长（有 friendlink:manage 权限），当有新友链申请时，收到通知，无需手动刷新后台 pending 计数。
6. 作为评论作者，当我的评论被审核通过后，收到通知。
7. 作为管理员，触发"立即抓取"订阅时，操作立即返回（不阻塞），抓取完成后通过通知告知结果（成功/失败）。

## Implementation Decisions

### 领域模型（domain/notification）

```go
// SourceType 通知来源类型（受控枚举，扩展时加常量 + subscriber 映射，不改 schema）
type SourceType string

const (
    SourceSubscriptionFailed SourceType = "subscription_failed"
    SourceFriendLinkApplied   SourceType = "friendlink_applied"
    SourceCommentApproved     SourceType = "comment_approved"
    // P2+ 按需扩展：SourceSubscriptionFetchDone / SourceUserLoginFailed / ...
)

// Notification 聚合根
type Notification struct {
    shared.AggregateRoot
    userID     shared.ID      // 接收者
    sourceType SourceType     // 通知来源类型（渲染分支 + 筛选）
    sourceID   shared.ID      // 关联资源 ID（如 comment_id / subscription_id）
    title      string         // 通知标题（快照，subscriber 生成）
    body       string         // 通知正文摘要（快照）
    payload    map[string]any // JSONB：类型特有字段（如 error_summary / post_title）
    readAt     *time.Time     // nil = 未读
}
```

- 不变量：`userID` 创建后不可变；`sourceType` 必须是受控枚举值；`readAt` 一旦设置不可回退（nil→time，不可 time→nil）。
- `payload` 用 Go struct + JSON tag 保证字段安全（JSONB 吸收新字段，零 migration 扩展新类型）。
- `title`/`body` 是写入时快照（subscriber 生成），不实时查关联资源——避免 N+1 查询。快照腐化风险（如文章改名后通知里还是旧标题）可接受：通知是"事件发生时的快照"，不是"当前状态的视图"。

### 数据库（migration 066 起）

- **066**：`notifications(id uuid pk, user_id uuid ref users on delete cascade, source_type varchar(50) not null, source_id uuid not null, title varchar(200) not null, body text not null default '', payload jsonb default '{}', read_at timestamptz null, created_at timestamptz not null default now())`。
  - 索引：`(user_id, created_at DESC)`（通知列表分页）、`(user_id, read_at) WHERE read_at IS NULL`（未读计数，部分索引）。
  - CHECK 约束：`source_type IN ('subscription_failed', 'friendlink_applied', 'comment_approved')`——加新类型时同步迁移扩展枚举。

### EventBus Subscriber（application/notification）

通知 subscriber 镜像审计 subscriber 的结构：

```go
// Subscriber 通知订阅者：消费领域事件 → 计算接收者 → 写通知 → SSE 推送。
type Subscriber struct {
    store    NotificationRepository
    notifier SSENotifier       // 推送给在线用户
    resolver RecipientResolver // 按 event 类型解析接收者
    log      zerolog.Logger
}

func (s *Subscriber) Subscribe(bus appshared.EventBus) {
    bus.Subscribe("", s.Handle) // 通配订阅，按事件类型分发
}
```

- **RecipientResolver**：按事件类型映射接收者规则。初版硬编码 switch：
  - `subscription.fetched`（失败时）→ 订阅所有者（`sub.UserID`）
  - `friendlink.created` → 有 `friendlink:manage` 权限的用户（查角色权限表）
  - `comment.approved` → 评论作者（查 comment 聚合的 author）

- **去重**：同一事件不重复写通知。用 `event.EventID()` 做幂等键（通知查重：`source_type + source_id + created_at` 窗口内已存在则跳过）。

### API（/api/v1，写操作走现有 SessionAuth + CSRF double-submit）

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/notifications?page=&limit=` | 登录 | 当前用户通知列表，分页 |
| GET | `/notifications/unread-count` | 登录 | 未读计数（SSE 断连时 fallback 轮询） |
| POST | `/notifications/{id}/read` | 登录 | 标记单条已读 |
| POST | `/notifications/read-all` | 登录 | 标记全部已读 |
| GET | `/notifications/stream` | 登录 | SSE 实时推送（心跳 30s + 断连补发） |

- SSE `Last-Event-ID`：客户端重连时带最后收到的通知 ID，服务端查 `WHERE user_id=$1 AND id > $lastEventId` 补发漏掉的通知。
- Nginx 配置：通知 SSE 路由需 `proxy_buffering off` + `X-Accel-Buffering: no`（code-runner SSE 路由已有先例）。

### 前端（FSD）

- `entities/notification`：Notification 类型 + 通知卡片组件（source_type → 图标/文案渲染分支）。
- `features/notifications`：
  - `NotificationBell`：HeaderNav 中的铃铛 + 未读 Badge + 下拉面板（最近 N 条 + "查看全部"）。
  - `useNotificationStream`：EventSource hook（自动重连 + 断连补发 + 未读计数乐观更新）。
  - `useNotifications`：TanStack Query 分页列表 hook（标记已读 mutation + 乐观更新）。
- `widgets/notifications`：通知中心页（可选 `/notifications` 全屏列表，P1 可用下拉面板替代）。
- `shared/api/notifications`：HTTP client 方法。

### 订阅抓取异步化（P2）

- `handler/subscription.go` 的 `Fetch` handler 改为：POST 立即返回 202 Accepted（`{ message: "抓取已开始" }`），`go func()` 在后台跑 `FetchNow`。
- 后台 goroutine 用 `context.Background()`（不绑 HTTP request context），完成后发布 `subscription.fetch_done` 事件（扩展领域事件，携带成功/失败 + entry 计数）。
- 通知 subscriber 消费 `subscription.fetch_done` → 给触发者写通知。
- 前端：mutation `onSuccess` 显示 toast "抓取已开始，完成后会通知你"。

### 装配

- `app/notification_container.go` 手工 DI，`make wire` 重新生成。
- 路由挂 `interfaces/http/routing/router.go` 登录区。
- `app/container.go` 中通知 subscriber `Subscribe(bus)`（平行于审计 subscriber）。

## Testing Decisions

- **领域**：`readAt` 不可回退不变量；`sourceType` 枚举校验。
- **subscriber**：三类事件（subscription_failed / friendlink_applied / comment_approved）正确解析接收者并写通知；未知事件跳过（不报错）；幂等去重（同一 EventID 不重复写）。
- **handler**：匿名 GET/POST 401；标记已读权限（只能标记自己的通知）；SSE 连接建立 + 心跳 + Last-Event-ID 补发。
- **前端**：铃铛未读数随 SSE 推送实时更新；标记已读后 Badge 消失；断连重连后补发正确。
- 不测：Nginx 配置、Redis pub/sub（P1 单实例不涉及）。

## Out of Scope

- **邮件通知**：预留扩展接口（`Notifier` 接口多实现），本 PRD 不实现。
- **Redis pub/sub 广播**：多实例水平扩展时加，当前单实例不需要。
- **通知偏好 / 聚合**：P3，记录决策待后续。
- **通知定期清理 job**：全保留策略下非必须，量级不是问题。
- **广播通知**：站级公告由 Announcement domain 独立处理，不进通知系统。
- **移动端 Push（FCM/APNs）**：不做。

## 难逆决策

- **非规范化单表 vs 规范化双表**：选单表。violet 90%+ 通知是 1:1，规范化双表的 JOIN 是纯负债，零存储收益。唯一受益场景（广播通知）由 Announcement domain 独立处理，不进通知系统。后期若出现高频广播场景需要改双表，是破坏性迁移。
- **写时扇出**：无条件写时扇出。violet 无 follow 关系，最大 fan-out = 通知管理员（几人），无 celebrity problem。读时扇出的复杂度（多源 JOIN + watermark 已读追踪）在 violet 是纯负债。
- **SSE vs 轮询**：选 SSE。复用 code-runner 已验证模式，实时性是现代通知系统预期。代价（多实例需 Redis pub/sub、断连补发）是可控工程问题，且单实例阶段不涉及。
- **payload 快照 vs 实时查关联资源**：选快照。通知是"事件发生时的快照"，不是"当前状态的视图"。快照腐化（文章改名后通知里是旧标题）可接受。实时查关联资源有 N+1 风险，对通知列表性能不友好。
- **受控枚举 source_type vs 自由字符串**：选受控枚举（Go 常量 + DB CHECK 约束）。扩展新类型需加常量 + 扩展 CHECK 迁移，但换来编译期安全 + 可筛选 + 统计能力。自由字符串的字段名拼写错误运行时才暴露。
