# PRD: 推文功能（tweets：多用户微博）

## Problem Statement

博客目前只有**长文（posts）**一种内容形态。登录用户想发短内容（碎片想法、日常、进度更新、一张图配一句话）没有载体——发成文章太重（标题/封面/TOC/版本历史），发成评论又必须依附文章。读者端也没有「最近动态」式的轻量浏览入口。

需要一个类 Twitter 的多用户微博能力：**任何登录用户可发推文，未登录可浏览**。

## Solution

新增独立 bounded context **`tweet`**，与 post / comment 平级：

- **多用户微博**：任何登录用户可发推文；无 follow 关系。
- **全局时间线** `/tweets`：全站推文按时间倒序，匿名可浏览。
- **用户主页** `/users/$username`：公开页，仅推文资料卡（头像/用户名/注册时间/推文列表）。
- **详情页** `/tweets/$id`：单条推文永久链接，P2 评论的落点。
- **内容模型**：纯文本（≤500 字）+ 最多 4 张图；文本与图片至少其一。
- **领域规则**：即发即出（无先审后发）；**不可编辑，只可删除**（作者删自己的，管理员凭 `tweet:delete-any` 删任意）；物理删除。
- **交互分三期**：P1 点赞；P2 评论/回复；P3 引用转发 + 话题标签。

### 交互分期

| 期 | 内容 | 可发布状态 |
|---|---|---|
| P1 | 发推文（文本+图）+ 全局时间线 + 详情页 + 删除 + 点赞 + 用户主页 | 最小可玩闭环 |
| P2 | 评论/回复（独立评论实体挂推文下，只在详情页出现） | 互动闭环 |
| P3 | 引用转发（转发本身是带 quote_of 引用的推文）+ #话题# 聚合页 | 传播闭环 |

## User Stories

1. 作为登录用户，我要在时间线顶部发一条纯文本或带图推文，发完立即出现在时间线最上面。
2. 作为登录用户，发图时要走站内上传管线（可选已有上传或新传），最多 4 张。
3. 作为访客（未登录），我要能浏览全站推文时间线、单条推文详情、某个用户的推文主页。
4. 作为登录用户，我要能删除自己发错的推文；推文不可编辑（删了重发）。
5. 作为管理员，我要能删除任意违规推文（前台对有权限者显示删除按钮）。
6. 作为登录用户，我要能给推文点赞/取消点赞，看到实时赞数。
7. 作为访客，我要能通过 `/users/sun` 看到用户 sun 的头像、用户名与其全部推文。
8. 作为读者，时间线加载更多时不因新推文插入而看到重复/漏数据（cursor 分页）。

## Implementation Decisions

### 领域模型（domain/tweet）

```go
// Tweet 聚合根
type Tweet struct {
    shared.AggregateRoot
    authorID shared.ID   // 作者，创建时固定，不可变
    content  string      // 纯文本，≤500 字（rune 计），与 images 至少其一非空
    images   []string    // 上传文件路径（/uploads/...），≤4 张
    likeCount int       // 冗余计数（tweet_likes 是唯一数据源，此列服务时间线列表性能）
    // P3 新增：quoteOf *shared.ID（引用推文 id）
}
```

- 不变量：`content` trim 后 ≤500 rune；`len(images) ≤ 4`；`content == "" && len(images) == 0` 拒绝；`authorID` 无 setter。
- 无 `Update` 方法——不可编辑是聚合根层面保证的（编译期无法改内容）。
- 发布时图片归属校验：每个 image path 必须对应 upload 域存在且 `owner == authorID` 的文件。application/tweet 定义 `TweetImageChecker` 端口，infrastructure 适配 upload 仓储（与 mcp.PostService 端口同构的依赖反转）。

### 数据库（migration 064 起，连续链）

- **064**：`tweets(id uuid pk, author_id uuid ref users, content text, images jsonb default '[]', like_count int default 0, created_at, updated_at)`，索引 `(created_at DESC, id)`（cursor 分页）、`(author_id, created_at DESC)`（用户主页）。
- **065**（T5）：`tweet_likes(tweet_id ref tweets on delete cascade, user_id ref users, created_at, pk(tweet_id, user_id))`。
- P2：`tweet_comments` 或复用 comment 聚合加 target 维度——实现期定，须 `on delete cascade`。
- P3：`tweets` 加 `quote_of uuid null ref tweets`；`tweet_hashtags` 关联表。
- **物理删除**：无 deleted_at。删除推文级联删点赞/评论。

### API（/api/v1，写操作走现有 SessionAuth + CSRF double-submit）

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/tweets?cursor=&limit=` | 公开 | 全局时间线，倒序 cursor 分页 |
| POST | `/tweets` | 登录 + 发布限流 | 发推文 `{content, images[]}` |
| GET | `/tweets/{id}` | 公开 | 详情（P2 起含评论数） |
| DELETE | `/tweets/{id}` | 作者或 `tweet:delete-any` | 物理删除 |
| GET | `/users/{username}/tweets?cursor=` | 公开 | 用户主页推文列表 |
| POST | `/tweets/{id}/like` | 登录 | 点赞（幂等） |
| DELETE | `/tweets/{id}/like` | 登录 | 取消点赞 |

- **cursor 分页**：`cursor = base64(created_at, id)`，查询条件 `(created_at, id) < cursor`。偏离项目 page/limit 惯例的理由：feed 顶部持续插入新数据，offset 分页会重复/漏数据（推特/Slack 均 cursor）。
- **发布限流**：独立限流维度（如 10 条/小时/用户），即发即出模式的防刷屏兜底，复用 middleware 限流先例（UploadRateLimit 同构）。
- **权限码**：新增 menu `tweet`、action `tweet:delete-any`，migration seed 进 permissions 表；超管通配符自动覆盖。发推文/删自己的/点赞不需要权限码，登录即可。
- 推文图片上传：复用 `POST /api/v1/uploads`（登录可用），`purpose=tweet`。

### 前端（FSD）

- `entities/tweet`：Tweet 类型 + `TweetCard`（头像/用户名/相对时间/正文/图片网格/赞数）。
- `features/tweets`：`TweetComposer`（发布框：textarea + 字数计数 + 图片选择/上传 ≤4）、时间线 hooks（`useInfiniteQuery` + cursor）。
- 路由：`tweets.tsx`（时间线）、`tweets.$id.tsx`（详情）、`users.$username.tsx`（用户主页，**全新公开页**，区别于登录私域 `/profile`）。
- `HeaderNav` 加「推文」入口。
- UI 直接写生产组件（跳过实验室原型），参照推特成熟卡片设计，用 shared/ui + react-bits 已装组件拼装。

### 装配

- `app/tweet_container.go` 手工 DI（同其它模块），`make wire` 重新生成。
- 路由挂 `interfaces/http/routing/router.go` 公开区 + 登录区。

## Testing Decisions

- **聚合根**：500 字边界、4 图边界、空内容+空图拒绝、authorID 无变更路径。
- **service**：发推文（含图片归属校验失败分支）、删除三分支（作者/有权限管理员/无权限他人）、cursor 分页边界（恰好一页/跨页/空）。
- **点赞**：重复点赞幂等（不双计）、取消未点赞不报错、删推文后赞级联清。
- **handler**：匿名 GET 通过、匿名 POST/DELETE 401、无 `tweet:delete-any` 删他人推文 403。
- 不测：jsonb 序列化细节、限流中间件本身（已有覆盖）。

## Out of Scope

- **follow 关系 / 关注首页流**：明确否决，全局时间线 + 个人主页即全部信息流。
- **编辑推文**：不可编辑是领域规则（推特原版语义），无编辑窗口、无版本历史。
- **先审后发**：即发即出，管理员事后删除兜底。
- **富文本 / markdown / 视频 / @提及 / 私信 / 通知**：均不做。
- **P2 评论、P3 转发与话题**：本 PRD 记录决策，实现在后续期 ticket。
- **推文管理后台页**：管理员在前台时间线/详情页直接删（有权限即见按钮），不建独立 admin 页。
- **推文图片防误删**（媒体库删图导致推文裂图）：发布时校验归属，删除保护留后续。

## 难逆决策

- **不可编辑**：聚合根无 Update 路径，一经发布内容不可变。推特色语义，规避「点赞/转发的是旧版内容」一致性问题；反悔路径 = 删除重发。后期若要加编辑需动聚合根 + 前端，成本高。
- **物理删除**：无软删回收站。评论/点赞级联物理删。审计追溯靠 audit 域事件（发推文/删除进审计），不靠业务表留尸。
- **即发即出**：无 pending 状态机。若垃圾内容成为问题，后期加状态列是破坏性迁移（存量全置 approved）。
- **cursor 分页**：偏离项目 page/limit 惯例，feed 场景的正确选择；后续评论区分页沿用 page/limit（评论流无顶部插入问题）。
- **评论独立实体而非「回复即推文」**：推特原版回复也是推文，但本项目选独立评论实体（复用 comment 域模式），评论不进时间线。模型更简单，代价是放弃「回复出现在自己主页」的推特行为。
- **新公开用户主页路由** `/users/$username`：此前站点无公开用户页概念，此路由成为第一个。

## 业界参考

- **不可编辑 + 删除重发**：X/Twitter 原版语义（编辑为付费功能且留历史，我们直接不做）。
- **cursor 分页防 feed 漂移**：[Slack API pagination](https://api.slack.com/docs/pagination)、Twitter API `max_id`/`since_id` 游标传统。
- **冗余计数字段**：点赞数放 tweets 表冗余列服务列表页，like 表为唯一数据源——标准计数器模式（counter cache）。
