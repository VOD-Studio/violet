# PRD: 吉祥物独立舞台特效重设计调研

## 调研目的

现有六个独立舞台特效（魔法阵、烟花、爱心雨、流星、闪耀、彩带）已经有可运行实现，但视觉语义彼此不够清楚，且粒子和控制按钮容易把舞台、角色与操作区挤在一起。本调研将一手设计系统、Web 动效规范和浏览器图形 API 的事实，转化为 Violet 可执行的特效规格。

本文把内容明确分成两类：

- **来源事实**：来源原文或官方规范直接表达的原则；每条均附原始 URL。
- **Violet 设计推论**：结合当前引擎结构做出的方案，不把推论冒充为来源规范。

## 当前项目事实

- `MascotStage` 是 `@violet/mascot/react` 的 React 宿主；`MascotTheater` 将独立舞台与导演台拆成两张卡片，表情导航由 `MascotLab` 作为桌面侧栏承载（见 `web/packages/mascot/src/react/MascotStage.tsx`、`web/src/features/lab/mascot/ui/components/MascotTheater.tsx`、`web/src/features/lab/mascot/ui/MascotLab.tsx`）。
- 特效接缝是 `EffectMounts`：`back` 画在角色身体下方、`front` 画在身体上方、`defs` 存放渐变定义；每个特效只需实现 `clear()`（见 `web/packages/mascot/src/engine/effects/types.ts`）。
- `StageFX` 已将五种一次性特效与 `MagicCircleFX` 的持续模式集中在同一个可扩展类中；彩带由 `Mascot` 独立管理,但沿用相同的 `EffectMounts` 与逐帧生命周期。
- 当前粒子基线为：魔法阵 2 个椭圆光圈 + 6 个星形粒子；烟花 3 组 × 12 个圆粒子；爱心雨 12 个爱心；流星 7 个；闪耀 1 个光圈 + 8 个星形粒子；彩带一次独立触发 3 条渐变流线。上述数量是实现事实，不是性能上限。
- 当前控制区先呈现 4 个基础动作，再呈现 6 个独立特效；`MascotTheater` 另有重播、巡演、偏航滑条和 AI 消息协议控制台。桌面端表情导航与舞台/导演台并列，导演台不再嵌入舞台；窄屏先显示表情导航，再显示舞台与独立导演台。

## 一手来源与可直接采用的事实

### 动效节奏与层级

1. **动效应传达状态、反馈或说明，而不是无目的装饰。** Apple HIG 将 motion 描述为用于传达状态、提供反馈和说明，并丰富视觉体验。[来源事实：Apple Human Interface Guidelines — Motion](https://developer.apple.com/design/human-interface-guidelines/motion)
2. **距离、速度和表面积变化应影响持续时间；短距离不应显得拖沓，长距离或大面积变化可以更长。** Material 指南明确要求使用动态时长，而不是所有动画共用一个时长。[来源事实：Material Design — Duration & easing](https://m1.material.io/motion/duration-easing.html)
3. **Material 的参考节奏是：移动端常规过渡约 300ms，入场约 225ms、离场约 195ms；超过 400ms 往往显得缓慢；桌面过渡通常 150–200ms。** 这是界面过渡的参考，不是对舞台粒子生命周期的硬性限制。[来源事实：Material Design — Duration & easing](https://m1.material.io/motion/duration-easing.html)
4. **自然的加速和减速应平滑且非机械；Material 提供 standard、deceleration、acceleration、sharp 等曲线。** 入场适合减速曲线，离场适合加速曲线。[来源事实：Material Design — Duration & easing](https://m1.material.io/motion/duration-easing.html)
5. **Web Animations API 将动画拆成 timing model 与 animation model，并为每个 Animation 提供播放控制。** 因此可把“触发、暂停、结束、清理”视为独立生命周期，而不是只改一个 CSS class。[来源事实：MDN — Web Animations API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Animations_API)

### 可访问性与减弱动态

6. **`prefers-reduced-motion` 表示用户要求删除、减少或替换非必要动效；放大、缩放和大范围平移可能触发前庭不适。** [来源事实：MDN — `prefers-reduced-motion`](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion)
7. **MDN 建议为动画提供暂停或禁用机制，并配合 `prefers-reduced-motion` 提供替代体验。** [来源事实：MDN — Web Animations API, Accessibility](https://developer.mozilla.org/en-US/docs/Web/API/Web_Animations_API#accessibility)
8. **WCAG 2.2 SC 2.2.2 要求：自动开始、持续超过 5 秒、且与其他内容并行的移动/闪烁/滚动内容必须有暂停、停止或隐藏机制；有多个运动元素时，提供一个同时控制它们的机制是最佳实践。** [来源事实：W3C — Understanding SC 2.2.2 Pause, Stop, Hide](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)
9. **WCAG 2.2 SC 2.3.3 要求交互触发的非必要 motion 可以被禁用；W3C 明确指出减少运动偏好是可行方案之一。** [来源事实：W3C — Understanding SC 2.3.3 Animation from Interactions](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)
10. **SVG `<animate>`、Web Animations API 的闪烁/闪现同样可能影响 ADHD、前庭障碍、癫痫、偏头痛和畏光用户。** [来源事实：MDN — SVG `<animate>` Accessibility concerns](https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Element/animate)

### SVG、粒子与性能

11. **Canvas 优化指南建议：重复图形可预渲染到 offscreen canvas；复杂场景可按静态背景、游戏层、UI 层分层；动画循环应使用 `requestAnimationFrame`，而不是 `setInterval`；应批量绘制、避免不必要状态切换和重绘。** [来源事实：MDN — Optimizing canvas](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas)
12. **同一 MDN 指南说明 CSS transform 通常更快，因为可使用 GPU；不透明背景可使用 `alpha: false` 让浏览器优化。** 这些结论直接适用于 Canvas；当前 Violet 是透明 SVG，因此不能照搬 `alpha: false`，但“静态层与动态层分离、只更新变化部分”的原则仍可作为 SVG 推论。[来源事实：MDN — Optimizing canvas](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas)
13. **SVG `<animate>` 能随时间改变 SVG 元素属性；它是单元素属性动画，不等同于粒子系统。** [来源事实：MDN — SVG `<animate>`](https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Element/animate)

### 控制分组与响应式排版

14. **Carbon 将按钮定义为触发动作的控件，按钮标签应表达交互后会发生的动作；只使用图标的按钮必须有准确代表动作的图标。** [来源事实：Carbon Design System — Button usage](https://carbondesignsystem.com/components/button/usage/)
15. **Carbon 建议建立按钮的视觉层级，一个界面通常只有一个高强调按钮；只有有关系的动作才应放在同一组，低强调按钮适合工具栏、列表和仪表盘等多动作场景。** [来源事实：Carbon Design System — Button usage](https://carbondesignsystem.com/components/button/usage/)
16. **Material Responsive UI 使用断点、列数、边距和 gutter 保持一致；窄屏可只显示一个内容层级，宽屏可显示 summary 与 detail 两层，并支持 reveal、transform、divide、reflow、expand、position 等重排方式。** [来源事实：Material Design — Responsive UI](https://m1.material.io/layout/responsive-ui.html)
17. **Material 的参考断点包括 480、600、840、960、1280、1440、1600dp；其网格在小屏使用 4 列，在更宽屏可使用 8 或 12 列。** [来源事实：Material Design — Responsive UI](https://m1.material.io/layout/responsive-ui.html)

## 现状问题诊断

### 视觉语义

**来源事实**：Apple 认为 motion 应用于状态、反馈和说明，而 Carbon 要求按钮标签表达动作。[Apple Motion](https://developer.apple.com/design/human-interface-guidelines/motion) · [Carbon Button](https://carbondesignsystem.com/components/button/usage/)

**Violet 设计推论**：五个特效不应只是“同一种粒子换颜色”。每种特效至少需要一个稳定的形状词、运动词和空间词：

| 特效 | 必须一眼读出的语义 | 形状/运动/空间锚点 | 不应出现的混淆 |
|---|---|---|---|
| 魔法阵 | 召唤、仪式、施法 | 脚下同心圆、分段符文、旋转方向相反、由地面向上吸附 | 不做满屏随机爆炸，不用烟花式径向散射作为主动作 |
| 烟花 | 庆祝、爆发、高潮 | 高处单点升空后停顿，中心闪白，再径向爆开，粒子带短尾并下坠 | 不从四周同时直线穿越，不让所有爆点同一时刻同一大小 |
| 爱心雨 | 亲昵、祝福、持续收到爱 | 爱心轮廓、从上至下、轻微横向摆动，前后景有大小差 | 不用圆点代替爱心，不让爱心从角色脚下向外爆发 |
| 流星 | 许愿、机会、快速掠过 | 单向斜线运动、头部亮点、线性渐隐拖尾、稀疏出现 | 不做垂直下落，不做多方向乱飞 |
| 闪耀 | 被聚焦、登场、完成提示 | 角色周围四/八向星芒，短促亮起后淡出，中心光环只扩张一次 | 不持续旋转整圈，不做高频闪烁或全屏白闪 |

### 动效层级

**来源事实**：Material 将运动分为进入、离开、位置变化和表面积变化，并要求不同距离使用不同持续时间。[Material Duration & easing](https://m1.material.io/motion/duration-easing.html)

**Violet 设计推论**：一段特效最多包含三层：

1. **舞台环境层（低频）**：光环、柔和色晕、地面投影，挂 `back`，不抢角色轮廓。
2. **主叙事层（中频）**：符文、爱心、流星头部、烟花中心，按语义挂 `back` 或 `front`。
3. **强调层（短促）**：闪白、星芒、爆点，挂 `front`，只在关键帧出现后迅速衰减。

`defs` 只保存可复用的渐变、滤镜或路径定义；粒子实体必须有本特效的回收路径，不能把临时节点留在共享挂载点。角色主体仍是唯一视觉主角，特效的最大不透明度建议低于角色关键轮廓的对比度。

## 六种特效的可执行规格

以下时长、数量和阈值是 Violet 的第一版验收规格，是设计推论，不是外部规范硬性数值。每条推论都以相应的一手来源为依据：动效节奏参考 [Material Duration & easing](https://m1.material.io/motion/duration-easing.html)，减弱动态参考 [MDN prefers-reduced-motion](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion)，粒子回收参考 [MDN Optimizing canvas](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas)。

### 1. 魔法阵：从地面召唤

- **触发与时序**：0–120ms 地面外环由透明到 0.65；120–480ms 两层环反向旋转并扩张约 8%；480–800ms 符文从环边缘向上浮起，随后在 900ms 内淡出。总时长约 1.7s，结束后回收所有节点。
- **视觉结构**：使用两层不连续圆环（外环 8–12 段、内环 6–8 段）和 6–8 个小星点；符文应沿切线方向排列，不再使用均匀散射的 10 个星形作为唯一辨识点。
- **挂载**：环与地面光晕挂 `back`；浮起的符文短暂挂 `front`；渐变放 `defs`。所有特效节点 `pointer-events="none"`。
- **减弱动态**：保留静态半透明环与少量符文，不旋转、不缩放，只执行 300–500ms 的 opacity 淡入/淡出。
- **验收**：不看按钮标签时，用户应能说出“脚下有一个正在施法/召唤的阵”；不应与闪耀（角色周围光环）混淆。

### 2. 烟花：升空、停顿、爆发、坠落

- **触发与时序**：可使用 2 个错时爆点而非固定 3 组同时出现。每组 0–260ms 上升并带 2–3 个尾粒子；260–340ms 短暂停顿；340–560ms 径向爆开；560–1,500ms 粒子受轻重力下坠并淡出。整段 1.5–1.8s。
- **视觉结构**：每组 10–14 条爆线/圆粒子，中心先出现一次高亮，再按 8–12 个方向散开；远景更小、更暗、更早淡出，近景更大但不覆盖脸部。
- **挂载**：升空尾迹与落下粒子挂 `back`；中心闪点与少量近景爆点挂 `front`；避免用全屏白色矩形模拟闪光。
- **减弱动态**：只保留两个静态爆点、短淡入淡出和小幅 opacity 变化；取消升空、缩放与高速径向位移。
- **验收**：必须读出“高处爆开后下坠”，而不是“随机彩色点”；同一触发中的爆点不能同帧、同半径、同颜色完全复制。

### 3. 爱心雨：持续但轻的祝福

- **触发与时序**：0–300ms 先出现 2–3 个前景爱心；300–2,800ms 分批落下；末尾 400ms 逐层淡出。总时长 3.2s，粒子速度低且横向摆幅小。
- **视觉结构**：8–12 个爱心，尺寸分为前景 4–6、后景 2–4；前景爱心有明确轮廓，后景只降低不透明度；轨迹为近似垂直落下加轻微正弦摆动。
- **挂载**：后景爱心挂 `back`，不遮挡角色脸部；前景最多 2–3 个挂 `front`，保持与角色轮廓分离。
- **减弱动态**：改成 3–5 个静态爱心点位和一次 600ms 淡入淡出，不使用从上到下的持续运动。
- **验收**：在缩略尺寸下仍能辨认心形；爱心雨是“从天而降的关怀”，不能变成普通彩色粒子雨。

### 4. 流星：一次方向明确的机会

- **触发与时序**：0–150ms 只显示头部亮点；150–650ms 沿左上→右下（或根据舞台宽度选择相反方向）穿越；650–900ms 拖尾先于头部淡出。每次触发 2–4 颗，延迟 90–180ms，避免 7 颗同时横扫。
- **视觉结构**：头部是 1 个高亮小点或短菱形，拖尾由 3–5 段逐级降低 opacity 的细线构成；速度方向、拖尾方向和颜色渐变必须一致。
- **挂载**：拖尾挂 `back`；头部和最后一颗高亮星挂 `front`；禁止覆盖角色眼睛超过约 120ms。
- **减弱动态**：保留一条静态斜向渐变短线与 1 次 300ms opacity 衰减，完全移除大位移。
- **验收**：用户能复述“从某个方向掠过”，而不是“屏幕上出现横线”；方向在同一会话内稳定，随机只作用于起点和间隔。

### 5. 闪耀：聚焦与完成

- **触发与时序**：0–120ms 角色周围光环淡入；120–300ms 4 个主星芒按上下左右错时亮起；300–650ms 8 个次级星点淡出；总时长不超过 900ms，不循环。
- **视觉结构**：使用四向长轴星芒作为主符号，四角小星为辅；光环只扩张一次，不能不断旋转或呼吸。与魔法阵的差异是“围绕角色的焦点”而非“脚下的几何仪式”。
- **挂载**：光环挂 `back`，主星芒挂 `front`；`front` 的最高亮度只持续一个短关键帧。
- **减弱动态**：保留静态光环和 4 个固定星芒，使用 450ms opacity 淡入/淡出，不做扩张、缩放和闪白。
- **验收**：用户应把它理解为“被聚光/完成提示”，不是烟花爆炸；不得产生连续闪烁。

### 6. 彩带：轻薄、独立的流线

- **触发与时序**：点击后立即生成 3 条错向流线；约 400ms 平滑展开，2.4s 内收束并回收，不要求角色正在自旋。
- **视觉结构**：以倾斜轨道投影表现前后层，头部略宽、尾部收细；使用低饱和渐变和有限弧长，避免彩带变成厚重的彩色圆环。
- **挂载**：前后段分别写入 `back` 与 `front`；渐变实体进入 `defs`；每条流线的路径与渐变在生命周期结束时一起移除。
- **减弱动态**：保留 3 条静态细线和 opacity 淡入淡出，不执行大范围缩放或高频旋转。
- **验收**：不看按钮标签时，用户应理解为独立的庆祝/祝福流线；角色静止时触发也应有完整的入场与退出阶段。

## 动效时序、数量与全局约束

- **来源事实**：Material 要求依距离、速度、表面积变化调整持续时间；MDN 要求动画可暂停/禁用并建议使用 `requestAnimationFrame`；WCAG 对自动运动超过 5 秒要求可暂停。[Material Duration & easing](https://m1.material.io/motion/duration-easing.html) · [MDN Web Animations API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Animations_API) · [W3C SC 2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)
- **设计推论：分层节拍**：单次点击触发应在 100–300ms 内给出可见反馈；主体叙事一般 0.8–1.8s；爱心雨可到 3.2s，但不能自动循环。巡演或任意自动连续触发必须提供全局“暂停特效”按钮。
- **设计推论：并发上限**：所有独立特效同时存在的实体节点建议不超过 48；单特效建议不超过 24（烟花 24–28 可作为例外，但需限制爆点数量）。新触发应优先回收同类旧粒子，不能无界追加。
- **设计推论：更新策略**：继续复用现有 `step(dt)`，只更新活动粒子的 transform、opacity 和必要属性；结束时立即从 DOM 移除。静态路径、渐变和滤镜进 `defs`，不要每帧创建 SVG 节点。粒子管理采用对象池或可复用节点时，必须保证 `clear()` 后没有旧状态泄漏。
- **设计推论：闪烁安全**：不使用 3Hz 以上的亮暗交替，不使用覆盖大面积舞台的纯白瞬闪；高亮只作为短促的单次强调。W3C 对闪烁阈值和非必要运动的解释见 [SC 2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html) 与 [SC 2.3.3](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)。

## 可访问性规格

1. **系统偏好**：使用 `prefers-reduced-motion: reduce` 作为默认减弱开关；JS 引擎应通过 `matchMedia` 或等价入口读取同一偏好。来源：[MDN prefers-reduced-motion](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion)。
2. **单次触发替代**：减弱模式不代表删掉语义。保留静态形状、颜色和一段 300–600ms 的 opacity 淡入/淡出，禁止大范围平移、缩放、旋转、连续下落和径向爆散。来源：[MDN prefers-reduced-motion](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion)。
3. **显式控制**：控制区增加“暂停特效/减少动效”全局控制；暂停时冻结粒子或立即切换到静态快照，恢复后不能重新堆叠旧粒子。W3C 建议多个运动元素共享一个暂停机制：[W3C SC 2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)。
4. **信息替代**：舞台应提供可读的当前状态文本（例如“已触发：流星”），且不依赖颜色、闪烁或运动作为唯一信息。按钮保留中文动作标签，图标只是补充。按钮标签原则来源：[Carbon Button usage](https://carbondesignsystem.com/components/button/usage/)。
5. **焦点与输入**：特效实体 `pointer-events="none"`；按钮保留可见 focus ring，键盘操作与点击触发同一入口；特效不应改变控制区尺寸或把焦点移入 SVG。项目当前已采用舞台布景不接事件的结构，应保持这一点（见 `MascotTheater.tsx`）。
6. **自动巡演**：巡演属于自动更新内容，应有暂停、停止或隐藏入口，并在减弱动态偏好下默认不自动启动。来源：[W3C SC 2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)。

## MascotTheater 控制区排版建议

### 分组与排序

**来源事实**：Carbon 要求只把有关系的 action 分组，并通过强调层级表达优先级；Material 支持窄屏 reflow、宽屏 divide/reveal。[Carbon Button usage](https://carbondesignsystem.com/components/button/usage/) · [Material Responsive UI](https://m1.material.io/layout/responsive-ui.html)

**Violet 设计推论**：控制区按用户任务分成四层，避免把“角色动作”和“舞台粒子”混成一排：

1. **播放层（顶栏）**：重播、巡演、暂停特效。重播与巡演是舞台播放控制，暂停特效是可访问性控制；三者使用同一组，但“暂停特效”在有运动时显示为高可见状态。
2. **角色动作层**：摸头、转圈、弹跳、撒花。这里是直接改变角色姿态/反馈的动作。
3. **独立特效层**：按“召唤 → 流线 → 掠过 → 爆发 → 亲昵 → 聚焦”的叙事排序：魔法阵、彩带、流星、烟花、爱心雨、闪耀。排序依据是设计推论，目标是让按钮顺序也能暗示视觉语义，不是把当前实现顺序当成规范。
4. **开发/协议层**：偏航滑条与 AI JSON 控制台作为导演台中的低优先级区域；默认不与面向展馆访客的舞台按钮竞争视觉层级，也不覆盖舞台。

每组有可读标题和短说明；不要只用分割线暗示分组。组内按钮统一尺寸、图标位置、标签格式。Carbon 特别提醒不要在同一 button group 混用尺寸：[Carbon Button usage](https://carbondesignsystem.com/components/button/usage/)。

### 响应式几何

- **窄屏（小于约 480px）**：舞台控制区使用 2 列网格；每个按钮保留图标与中文标签，必要时让标签自然换行但不截断。导演台与协议区置于舞台之后的独立卡片内，不挤占舞台首屏；表情导航优先显示。
- **中屏（约 480–839px）**：角色动作使用 4 列，独立特效使用 2 或 3 列，并让所有按钮等宽；舞台标题与播放控制允许换成上下两行。
- **宽屏（约 840px 及以上）**：角色动作使用 4 列，独立特效使用 2 列；表情导航固定在舞台右侧，导演台作为舞台下方的独立卡片。Material 的官方断点、列数与 reflow 原则见 [Responsive UI](https://m1.material.io/layout/responsive-ui.html)。
- **布局实现建议**：优先使用 `grid-template-columns: repeat(auto-fit, minmax(...))` 或明确断点，而不是把按钮硬塞进固定列；按钮标签长度变化时不应引起舞台高度抖动。控制区容器继续使用 `min-width: 0`，防止长协议文本撑破布局。
- **触控与键盘**：按钮至少提供稳定、可点击的高度和间距；视觉上不要把相邻按钮合并成不可分辨的色块。焦点环不得被 `overflow: hidden` 裁切。图标与文字同时保留，以免仅凭图标猜动作。图标语义原则见 [Carbon Button usage](https://carbondesignsystem.com/components/button/usage/)。

### 视觉层级

- 主色强调只给当前激活状态或暂停/恢复状态，不给六个特效按钮同时上高饱和色；这对应 Carbon 的“建立单一高强调动作”原则。[Carbon Button usage](https://carbondesignsystem.com/components/button/usage/)
- 独立特效按钮使用同一基础样式，通过图标和标签区分语义；不把按钮颜色直接绑定粒子颜色，避免用户把控件颜色误当作状态。
- 控制区与舞台保持间距和独立背景，特效只在 SVG 舞台内播放；`MascotTheater` 使用舞台卡片与导演台卡片两层结构，`MascotLab` 负责表情导航的常驻侧栏。
- 交互反馈使用边框、背景、颜色和可见焦点环；不使用 hover 上移、active 缩放等装饰性位移，避免控件产生跳动或拉伸感。

## 实施边界与验收清单

- 六种特效在静态首帧、完整播放和减弱动态模式下都有不同的视觉语义；仅看舞台不看标签也能区分至少四种，且魔法阵与闪耀不混淆。
- 每种特效都有明确的入场、主体、退出阶段；无无限循环、无节点泄漏、无超过 3Hz 的闪烁；自动巡演可由一个全局控制暂停。
- 同时触发多个特效时活动节点不超过 48；触发新一轮时旧粒子按同类优先回收；`clear()` 后 `back/front/defs` 没有残留临时节点或错误渐变引用。
- `prefers-reduced-motion: reduce` 下不出现大范围位移、旋转、缩放或径向爆散；仍保留可辨认的静态形状和淡入淡出。
- `MascotTheater` 的舞台、导演台与表情导航在窄、中、宽三种宽度下不发生横向溢出、标签截断或舞台高度跳动；分组标题、按钮标签、键盘焦点和暂停状态可被读屏/键盘用户理解。
- 视觉验证应以浏览器实际舞台为准：依次触发六种效果、开启减弱动态、暂停巡演、改变窄屏宽度，并观察节点是否按生命周期消失。本文同时记录已落地的引擎与导演台改动,不是仅供阅读的设计草案。
