# PRD: 账号关联与合并

## Problem Statement

同一用户在 violet 可能持有多个账号。当前 OAuth 登录（`application/auth/command/google_login.go`、`github_login.go`）以 email 为唯一身份关联键：匹配到已有账号则静默绑定 provider id，匹配不到则建新号。由此产生三类问题：

1. **重复账号**：用户注册用邮箱 A，GitHub primary 是邮箱 B → GitHub 登录直接建第二个号；再来一次就三个。生产库已有真实用户的重复账号。
2. **安全洞**：`github_login.go:147-149` 在找不到 primary+verified email 时兜底取 `emails[0]`——可能是**未验证 email**，拿来匹配已有账号等于允许「在 GitHub 挂别人邮箱」接管 violet 账号。
3. **绑定后失联**：两个 handler 都只按 email 查用户、从不按 provider id 查（`google_login.go:87`、`github_login.go:164`）。用户绑定后改了 Google/GitHub 侧 primary email，下次登录 email 匹配不中 → 走建号分支 → `SetGoogleID/SetGithubID` 撞 users 表 uniqueIndex → Save 报 500。

同时登录方式管理是半成品：`web/src/features/profile/ui/ConnectionsSection.tsx` 的「登录方式」卡片纯展示（注释明示「绑定/解绑 OAuth 本轮不提供操作入口」），`UserDTO` 的 `has_password/google_bound/github_bound` 字段已就绪但没有操作链路。

## Solution

三层改动：登录关联策略收紧（安全优先）→ 设置页绑定/解绑补全（用户自主管理）→ 管理员账号合并（存量数据治理）。

### 复用基线（本次不重写）

- users 表已内嵌 OAuth 绑定列：`GoogleID/GithubID *string uniqueIndex`、`GithubLogin`（`infrastructure/persistence/gorm/model/base.go:47-49`），无独立 identity 表——两个 provider 的体量下**不引入 identity 表**，绑定/解绑即操作这三列。
- `User.ReconstructUser`/`SetGoogleID`/`SetGithubID`/`SetGithubLogin` 等实体方法与 `UserRepository.FindByEmail` 已存在；需新增 `FindByGoogleID/FindByGithubID`。
- 前端 `ConnectionsSection`（profile security tab）即绑定/解绑 UI 挂载点；`UserDTO` 绑定状态字段已在。
- 登录 UI 三处入口：`web/src/features/auth/ui/LoginDialog.tsx`（弹窗）、`web/src/routes/login.tsx`（页面）、`web/src/routes/auth.github.callback.tsx`（GitHub 回调）。
- 管理后台用户列表 `web/src/routes/admin.users.tsx`（行操作模式：EditUserDialog 等），合并入口照此挂载。
- forgot/reset-password 邮箱验证流程可作无密码账号的补密码通道；`PATCH /auth/password`（ChangePassword，需旧密码）覆盖有密码用户。
- audit 域已有操作日志，合并动作写审计。

### 架构

```
OAuth 登录（改造后统一顺序）
    │
    ① 按 provider_user_id 查（google sub / github id）
    │   命中 → 直接登录（不依赖 email，修复「绑定后失联」）
    │
    ② 按 email 查（仅已验证 email）
    │   命中且 provider 未绑定 → 返回 409 link_confirmation_required
    │       ├─ 前端弹「输入密码确认绑定」
    │       │    POST /auth/link/confirm {link_token, password}
    │       │    密码对 → 绑定 + 登录；无密码账号 → 引导邮箱补设密码
    │       └─ link_token = Redis 一次性短 TTL 凭证，承载已验证的 provider 身份
    │   命中且已绑定（同 email 不同 provider id，罕见）→ 拒绝，提示联系管理员
    │
    ③ 都未命中 → 建新号（现状保留）
    │
GitHub email 获取：只认 /user/emails 中 primary+verified；
    token 请求显式申请 read:user user:email scope；
    拿不到有效 email → 拒绝登录（删除 emails[0] 兜底）
```

### 关键设计

**登录查找顺序反转：provider id 优先于 email**

绑定语义的正确锚点是 provider_user_id（不变），email 只是首次关联的匹配键。顺序改为 ①`FindByGoogleID/FindByGithubID` ②`FindByEmail`。这同时消解了「用户改 provider email 后撞 uniqueIndex」的 500。

**两阶段绑定确认，link_token 承载中间态**

GitHub 的 code 一次性、Google 的 credential 短时效，用户输密码期间不能重放原始凭证。第一阶段（`POST /auth/google`、`/auth/github`）在「需确认」分支已完成 code 换 token、拉取 provider 用户信息，将 `{provider, provider_user_id, email, login, avatar}` 存 Redis（key `link:<token>`，随机 ≥256-bit，TTL 5min，一次性），返回 `{link_token, email, has_password}`。第二阶段 `POST /auth/link/confirm` 验密码 → 绑定 → 建 session；密码错可重试（不消费 token，限次）；超时则整个 OAuth 流程重来。

**无密码账号的确认分支**

Google 建号用户（空哈希）用 GitHub 登录撞上确认流时无密码可输：返回体带 `has_password=false`，前端提示「该账号未设置密码，请先通过邮箱验证设置密码后再绑定」，引导走既有 forgot-password 链路。不在 OAuth 弹窗里内嵌注册式表单。

**解绑约束**

`DELETE /auth/connections/{provider}` 前置校验：解绑后必须仍存在至少一种登录方式（`has_password` 或剩余 OAuth 绑定 ≥1），否则 400。密码侧不设解绑，只有改密/重置。

**合并 = 单事务迁移 30 张表 + 冲突折叠**

`POST /admin/users/merge {primary_id, secondary_id}`：secondary 的全部 user 归属行改写为 primary，随后删 secondary。归属列全景（scout 实测，`infrastructure/persistence/gorm/model/`）：

- 内容：posts.author_id、post_versions.editor_id（操作人语义，随迁）、comments.created_by、comment_reactions.user_id、announcements.created_by、notes/tweets/tweet_comments/series/galleries.author_id、tweet_likes.user_id、files.owner_id、upload_sessions.user_id
- 偏好/凭证：comment_reactions、tweet_likes、custom_emoji_favorites、chat_read_positions（复合主键含 user_id）、api_tokens.user_id、chat_bots.user_id（uniqueIndex）
- 通知/订阅：notifications.user_id（uniqueIndex(event,user)）、notification_push_subscriptions、chat_push_subscriptions、subscriptions.user_id
- 社交/聊天：friendlinks.user_id（可空）、personas.created_by、custom_emojis.owner_id、chat_conversations.owner_id、chat_conversation_members.user_id、chat_messages.sender_id、chat_message_reactions.user_id、chat_events.user_id、chat_direct_pairs（user_a_id+user_b_id 双列）

冲突策略：复合唯一键下 primary/secondary 各有一行 → 删 secondary 侧保留 primary 侧；users 表 OAuth 列 secondary 有值而 primary 已占 → 保留 primary 的绑定，secondary 侧丢弃（该 provider 账号此后登录会走「按 provider id 未命中 → email 匹配」正常路径）；email/username/角色等账号本体字段一律保留 primary。`chat_direct_pairs` 合并后出现 user_a==user_b 自环或重复 pair → 删除。合并不可逆，前置审计 + 管理台输入 secondary 用户名二次确认。

## 接口契约

### POST /auth/google | POST /auth/github（扩展响应）

匹配到已有账号且需密码确认时返回 `409`：

```json
{
  "code": "link_confirmation_required",
  "link_token": "<256-bit>",
  "email": "a***@x.com",
  "has_password": true
}
```

拿不到已验证 email（GitHub）：`400`，message 为规范文案（见「文案规范」）。

### POST /auth/link/confirm

- **请求**：`{link_token, password}`（AuthRateLimit）
- **成功** `200`：绑定 + 下发 session cookie（与登录同构，复用 CreateSessionHandler）
- **错误**：token 无效/过期 `410`；密码错误 `401`（token 不消费，累计 5 次后作废）；账号被禁用 `403`

### POST /auth/connections/{google|github}（绑定，需登录态）

- google：`{credential}`（沿用现有 userinfo 验证方式取 sub/email）
- github：`{code}`（服务端换 token 拉 id/login/email）
- 校验：provider 身份未绑定到**任何**账号（含他人）→ 已被占用 `409`（body 带 options 语义：占用方是否当前用户）
- 成功 `200`：返回最新 `google_bound/github_bound`

### DELETE /auth/connections/{google|github}（解绑，需登录态）

- 解绑后无任何登录方式 → `400`（message 说明需先设置密码或绑定其他方式）
- 成功 `200`

### POST /admin/users/merge（需 `user:update` 权限）

- **请求**：`{primary_id, secondary_id, confirm_username}`（confirm_username 必须等于 secondary 用户名）
- 行为：单事务迁移 + 冲突折叠 + 删 secondary + 写审计日志
- **错误**：任一 id 不存在 `404`；confirm 不符 `400`；primary==secondary `400`；内置超管参与 `403`

## 文案规范

- GitHub 无有效邮箱（拒绝）：`GitHub 账号未提供已验证的主邮箱，无法完成登录。请在 GitHub 设置的 Emails 页将常用邮箱设为已验证的主邮箱后重试。`
- 首次匹配确认（弹窗标题）：`该邮箱已注册账号`；正文：`输入账号密码确认绑定 {provider}，绑定后可使用 {provider} 直接登录。`
- 无密码分支：`该账号未设置密码，请先通过「忘记密码」邮箱验证设置密码，再回来完成绑定。`

## 安全考虑

- **未验证 email 一律不得作为关联键**（本次修的核心洞）：GitHub 只认 primary+verified，删除 `emails[0]` 兜底。
- link_token：高熵随机、Redis TTL 5min、一次性（confirm 成功即删）、密码错限 5 次，防在线爆破。
- 绑定端点必须校验 provider 身份未被任何账号占用（uniqueIndex 之外的显式校验 + 友好 409），防止把自己 OAuth 绑到他人账号的语义混乱。
- 合并端点为高危不可逆操作：权限点收窄、confirm_username 二次确认、全量审计。
- GitHub OAuth scope 显式申请 `read:user user:email`，否则隐私用户连 emails 列表都拿不到。

## 测试策略

### 后端

- GitHub email 策略：primary+verified 命中；无 scope/隐私 → 规范拒绝；**emails[0] 兜底行为删除**（回归：未验证 email 不再触发建号/关联）。
- 登录顺序：绑定后改 provider email 再登录 → 按 provider id 命中直接登录（回归修复撞 uniqueIndex 的 500）。
- 确认流：409 响应字段齐全；confirm 密码对/错/超时/限次；无密码账号返回 has_password=false 分支。
- 绑定/解绑：他人占用 409；解绑后无登录方式 400；正常绑定/解绑往返。
- 合并：30 表迁移断言（重点 comment_reactions/tweet_likes/custom_emoji_favorites 复合键折叠、chat_direct_pairs 自环删除、OAuth 列冲突保留 primary）；confirm_username 校验；审计落库。

### 前端

- LoginDialog/login.tsx/github 回调三处的确认弹窗流（409 → 弹窗 → confirm → 登录态）。
- ConnectionsSection 绑定按钮 → OAuth 流 → 回调绑定；解绑约束提示。
- admin.users.tsx 合并对话框（选主号 + confirm_username）。

## 已确认事项（访谈决策）

1. 首次匹配必须输密码确认才绑定（不做静默自动关联）；provider 已绑定的直接登录。
2. GitHub 无已验证邮箱 → 拒绝登录，规范文案提示，不用大白话。
3. 设置页提供绑定/解绑（方案 1 + 2 组合）。
4. 无密码账号的确认分支走「邮箱补设密码」引导，不内嵌表单。
5. 存量重复含真实用户 → 需要完整合并能力，管理员后台触发（不做用户自助合并）。
