# PRD: 自定义表情与收藏（聊天/评论/推文）

## Problem Statement

聊天/评论/推文共用同一套表情选择器与渲染机制，但表情来源只有两条：B 站表情包同步 + 站长后台手工建的分组（`emoji:create`/`emoji:manage-group` 权限）。普通用户没有任何自定义/上传表情的能力，看到别人发的、自己没有的表情时也没有"收进自己表情库"的手段。

## Solution

新增"自定义表情"概念，与现有 admin 维护的"系统表情"并列但模型独立：自定义表情默认私有（只有上传者可选用），他人在聊天/评论/推文内容中看到渲染结果但不能直接选用，除非通过右键"收藏"获得选用权（引用式，非拷贝）。收藏与自传共享同一份额上限（默认 100，后台/env 可调）。右键菜单是全站挂载的通用 UI 原语，只在自定义表情图片上追加"收藏到我的表情"这一项，其余目标（系统表情、非表情内容）右键行为不变。表情渲染 token 按 ID 解析（镜像 PRD-0019 已在用的 `![img:<uuid>]` 内嵌图片占位符先例），系统表情继续按名称解析，两套 token 互不冲突、可在同一段文本共存。

## User Stories

1. 作为登录用户，我想在聊天/评论/推文的表情选择器里看到一个"我的表情"标签页，这样能快速找到自己传的和收藏的表情。
2. 作为登录用户，我想在"我的表情"标签页里传一张图作为自定义表情，这样能用自己喜欢的图当表情发。
3. 作为登录用户，我想给自己传的表情起个名字，这样在选择器里好识别、也能被占位符渲染。
4. 作为登录用户，我想上传的表情不要求全站唯一命名，这样不会因为别人先用了"doge"这个名字而传不了。
5. 作为登录用户，我想我传的表情默认只有我自己能在选择器里选用，不会一传上去就被全站任何人直接使用。
6. 作为聊天/评论/推文的读者，我想看到别人发出的自定义表情时能看到渲染出来的图，即使我还没收藏它。
7. 作为聊天/评论/推文的读者，我想右键点击别人发的、我还没收藏的自定义表情，弹出一个"收藏到我的表情"选项。
8. 作为登录用户，我想点了"收藏到我的表情"之后，这个表情立即出现在我自己的"我的表情"标签页里、可以选用发送。
9. 作为登录用户，我想右键自己已经收藏过的表情时，菜单显示"移出我的表情"而不是重复收藏。
10. 作为登录用户，我想右键自己上传的表情时，菜单显示"删除表情"而不是"收藏"（收藏自己的东西没有意义）。
11. 作为登录用户，我想右键系统表情（B 站包）或非表情内容时，右键行为和今天完全一样（原生浏览器菜单），不被新功能打断。
12. 作为登录用户，我想收藏是"引用"而不是"拷贝"——如果对方删了原表情或被管理员下架，我的收藏也应同步消失，而不是留一个我抢救下来的副本。
13. 作为登录用户，我想我的表情份额（自传 + 收藏合计）有上限，超过上限时上传/收藏应该报错提示我先清理旧的。
14. 作为管理员，我想能在后台调整这个份额上限的数值，不用改代码重新部署。
15. 作为运维人员，我想份额上限有一个部署期 env 变量兜底默认值，后台没配置时用这个默认值。
16. 作为登录用户，我想在"我的表情"标签页里直接删除自己上传的表情、或移出一个我收藏的表情，不需要额外去一个新页面找。
17. 作为管理员，我想能强制下架任何用户的违规自定义表情（不限于自己上传的），下架后所有收藏者同步失效。
18. 作为登录用户，我想已经发出去的历史消息/评论/推文，如果里面用到的自定义表情后来被删除/下架，渲染上要有合理的兜底（显示原始占位文本），而不是报错或空白。
19. 作为登录用户，我想在评论区、推文正文、推文回复、聊天输入框、聊天表情回应——这五处能触发表情选择器的地方，都能看到并使用"我的表情"。
20. 作为登录用户，我想上传自定义表情的文件类型/大小限制和现有表情上传一致（jpg/png/gif/webp，10MB 上限），不用重新学一套规则。
21. 作为登录用户，我想上传/删除/收藏这些操作只需要登录，不需要额外的权限申请或审核等待。
22. 作为开发者，我想系统表情的 `[name]` 渲染和解析规则完全不受影响，这次改动对已有表情包/颜文字的展示零回归。
23. 作为聊天用户，我想别人发的带自定义表情的消息通过 SSE 实时推送过来时也能立即正确渲染，不用刷新页面才显示出来。
24. 作为开发者，我想评论域和推文域现有两份几乎相同的表情按名查找适配器，这次新增的"按 ID 查自定义表情"逻辑只实现一次、被三个域共享，不要变成第三份重复代码。

## Implementation Decisions

### 领域模型：`domain/customemoji`（新增，独立于 `domain/emoji`）

```go
// CustomEmoji 聚合根
type CustomEmoji struct {
    shared.AggregateRoot
    id        shared.ID  // UUID，与 upload.File/Tweet 同构；token 内嵌该 ID，格式镜像 PRD-0019 的 ![img:<uuid>] 先例
    ownerID   shared.ID  // 上传者，创建时固定不可变
    name      string     // 展示名，同一 ownerID 下唯一（而非全局唯一），用于 [name:id] 中的展示部分
    url       string     // 图片 URL（/uploads/...），复用现有 upload.File 落盘路径与校验
    createdAt time.Time
    deletedAt *time.Time // 软删除；自行删除与管理员下架走同一字段，不区分原因
}
```

- 不变量：`name` trim 后非空；同一 `ownerID` 下 `name` 唯一（防自己列表里困惑），**不做全局唯一校验**——这是相对现有 `domain/emoji.Emoji`（全局按名解析）最大的语义差异。
- 收藏关系落一张独立关联表，不建模成 `CustomEmoji` 聚合内部集合——收藏是"谁收藏了谁的表情"的多对多关系，不属于表情自身的不变量，镜像历史上 `user_favorite_stickers`（migration 010，已随 stickers 整表删除）的表结构。
- 无 `Update` 方法——名字/图片一旦创建不可改；改名/换图 = 删除重传（和 Tweet"不可编辑，只可删除重发"同构，保持简单）。

### 数据库（migration 092 起）

- **092**：`custom_emojis(id uuid pk, owner_id uuid ref users on delete cascade, name varchar(50) not null, url varchar(512) not null, created_at, deleted_at)`，唯一索引 `(owner_id, name) where deleted_at is null`。
- **093**：`custom_emoji_favorites(user_id uuid ref users on delete cascade, emoji_id uuid ref custom_emojis on delete cascade, created_at, primary key(user_id, emoji_id))`，索引 `idx_custom_emoji_favorites_user(user_id)`。
- `site_settings` 是纯 key-value 表（无固定列），新增 `custom_emoji_max_per_user` 配置键不需要迁移。

### 权限点

- 上传/删除自己的/收藏**不新增权限点**——和聊天发消息一样，只需要 `SessionAuth`。
- 新增 `customemoji:manage`（"管理自定义表情"），用于管理员强制下架任意用户的自定义表情（`DELETE /custom-emojis/{id}`，`actor != owner` 时要求该权限），命名与授权方式对齐 `chat:manage`/`comment:delete`。

### 站点设置

- `domain/settings.SiteSettings` 新增 `CustomEmojiMaxPerUser int`（`json:"custom_emoji_max_per_user"`，注释同 `CodeRunnerMaxCPUCores`："0 表示未配置，消费方 fallback 到 env config"）。`fromMap`/`UpdateInput`/`application/settings` 的 `GeneralView` 三处按 `CommentsModeration` 的接线方式补齐。
- 新增 env 变量 `CUSTOM_EMOJI_MAX_PER_USER`（默认 `100`），仅当 site_settings 未配置（值为 0）时生效，读取时机与 `CodeRunnerMaxCPUCores` 消费方（`application/coderunner/service.go` 的 fallback 分支）同构。

### API（新增，均挂 `SessionAuth`）

- `POST /custom-emojis`：body `{name, url}`（`url` 来自已有 `POST /uploads/emoji` 上传结果，复用现有 10MB + jpg/png/gif/webp 校验，不新增上传端点）。校验：`(owner_id, name)` 唯一、当前份额（自传+收藏）未超过 `custom_emoji_max_per_user`。
- `GET /custom-emojis/mine`：返回 `{owned: CustomEmoji[], favorited: CustomEmoji[]}`，供 `EmojiPicker`"我的表情" tab。
- `POST /custom-emojis/{id}/favorite` / `DELETE /custom-emojis/{id}/favorite`：收藏/移出；favorite 校验份额上限、且不能收藏自己的表情（无意义操作直接拒绝）。
- `DELETE /custom-emojis/{id}`：删除；`actor == owner` 或持有 `customemoji:manage` 均可执行，软删除（`deleted_at`），级联效果由**读路径**体现（下方解析规则），不需要额外清理收藏关联行。

### 表情解析：共享 resolver + 三域各自的薄 adapter

- 新增 `application/customemoji` 提供 `ResolveByIDs(ctx, ids []uuid, viewerID shared.ID) (map[uuid]CustomEmojiRef, error)`，`CustomEmojiRef` 含 `URL`、`OwnerID`、`Relation`（`owned`/`favorited`/`none`——`none` 表示 viewer 未拥有也未收藏，仍返回 URL 供渲染，但前端据此只显示"收藏"菜单项、不显示"删除/移出"）。
- `comment_container.go`/`tweet_container.go` 现有 `emojiLookupAdapter`/`tweetEmojiLookupAdapter` 的 `FindByNames` 增加分支：token 含 `:` 且冒号后段是合法 UUID 时，委托给共享 resolver；否则走现有系统表情按名查找逻辑不变。两条分支合并进同一个 `map[string]EmojiRef` 返回值，调用方（`enrichEmotes`）无感知。
- 聊天不复用 `emojiLookupAdapter`（它是客户端全局 map 架构），但复用同一个共享 resolver：`MessageDTO`/SSE `EventDTO` 新增 `CustomEmote map[string]CustomEmojiRefDTO` 字段（命名与含义镜像评论 `Emote`），由 `chat.Service` 在 `toDTO`/`notifyEvents` 路径解析消息 `content` 里的 `[name:uuid]` token 后填充，系统表情继续走现状的客户端全局 `GET /emojis` 路径不变。新消息通过 SSE 推送时同样携带 `CustomEmote`，前端不需要额外请求。
- `EmojiText.tsx`（评论+推文共用）与 `ChatMessageContent.tsx`/`chat-markdown.ts` 的 token 匹配正则**不需要改动**——`/\[([^\]]+)\]/g` 已经把括号内内容当不透明字符串整体做 key，`[name:uuid]` 天然被同一条正则捕获，只是 map 里多一种 key 形态。渲染时按 `Relation` 字段决定该 `<img>` 是否挂右键菜单触发属性。

### 表情插入（前端）

- `Emoji` 前端读模型新增可选字段 `custom_emoji_id?: string`、`relation?: "owned" | "favorited"`，仅"我的表情" tab 返回的条目携带。
- `useRichTextInput.insertEmoji`（评论/聊天输入/推文回复共用）与 `TweetComposer.tsx` 的独立 `handleEmojiSelect`：两处都改为——`emoji.custom_emoji_id` 存在时插入 `` `[${emoji.name}:${emoji.custom_emoji_id}]` ``，否则维持现有 `` `[${emoji.name}]` ``。

### `EmojiPicker` 组件

- 新增内部数据源：已登录时额外发起 `GET /custom-emojis/mine` 查询，渲染一个"我的表情" tab（未登录不显示该 tab）。
- Tab 内提供上传入口（复用现有 `/uploads/emoji` + 新 `POST /custom-emojis` 两步）；删除/移出交由右键菜单处理，不在 tab 内重复造轮子。
- 四处既有调用方（`RichCommentInput` 内嵌的评论/聊天输入/推文回复、`ChatWorkspace` 表情回应、`TweetComposer` 推文正文）零改动——`EmojiPicker` 自给自足获取个人数据，不需要新增/穿透 props。

### 全站右键菜单（新 UI 原语）

- 新增 `web/src/shared/ui/base/context-menu.tsx`，照 `dropdown-menu.tsx` 的 radix-ui 封装约定。
- 挂载点：`web/src/providers.tsx` 的 `AppProvider`，包一层全局 `ContextMenuTrigger`（覆盖 `{children}` 全部子树），`ContextMenuContent` 按被右键的目标动态决定菜单项——检测目标 `<img>` 是否带 `data-custom-emoji-id` 属性（`EmojiText`/`ChatMessageContent` 渲染自定义表情时附加该属性，系统表情不附加），没有该属性时不弹出自定义菜单（不 `preventDefault`，浏览器原生右键行为直接生效）。
- 菜单项按 `relation` 决定：`none` → "收藏到我的表情"；`favorited` → "移出我的表情"；`owned` → "删除表情"。

## Testing Decisions

### 测试原则

只测外部行为：领域不变量（份额、命名唯一性、软删除级联可见性）、应用层用例（资源解析的三分支：系统表情/自定义-属于我/自定义-属于别人）、关键前端行为（token 插入、右键菜单按 relation 出不同项）。不测 radix-ui 内部实现、不测样式。

### 测试 Seam

| Seam | 层级 | 覆盖 |
|---|---|---|
| `domain/customemoji` 单测 | 领域实体 | 创建校验（空名拒绝、同 owner 重名拒绝、跨 owner 同名允许）；软删除后判定为不可选用 |
| `application/customemoji` 集成测试 | 应用服务 | 上传超份额拒绝（自传+收藏合计口径）；收藏自己的表情拒绝；收藏后份额计数正确；下架后 `ResolveByIDs` 对该 ID 返回未命中（而非报错） |
| `application/comment`（`enrichEmotes`）/`application/tweet` 回归测试 | 应用服务 | 正文含 `[name:uuid]` token 时，`Emote` map 命中共享 resolver 分支；含普通 `[name]` 时行为与现状完全一致（零回归） |

## Out of Scope

- **系统表情收藏**：收藏动作只对自定义表情成立，系统表情本就人人可选。
- **公开表情画廊/浏览发现**：收藏入口只能是"在评论/推文/聊天内容里遇到并右键"，不做独立的可浏览表情市场页。
- **预审核队列/NSFW 检测**：自定义表情上传即可用（私有范围内），不新增内容审核流程；风险基线和现有"图片消息零审核"一致。
- **收藏通知**：上传者不会收到"某人收藏了你的表情"的站内通知。
- **独立表情管理页面**：管理（删除/移出）复用 `EmojiPicker`"我的表情" tab 内的右键菜单，不建单独设置页。
- **收藏与上传分别计数的配额**：两者共享同一份额上限，不设第二个独立数字。
- **吉祥物（mascot）自定义表情包**：与 PRD-0017 P2 计划中的"表情包自定义"是完全不同的功能（前者是站内虚拟吉祥物挂件的表情素材，后者是本 PRD 的用户聊天/评论/推文内容表情），文字撞车但域不同，不要混为一谈。

## Further Notes

### 与现有表情基础设施的关系

自定义表情不是"系统表情的一种"，是并列的独立聚合；两者只在**渲染层**（`EmojiText`/`ChatMessageContent` 的 token 匹配正则、`EmojiPicker` 的选择器 UI）汇合，数据模型、生命周期、权限模型完全独立。这是相对"扩展现有 `domain/emoji`"方案的核心取舍，详见 ADR-0013。

### Token 格式先例

`[name:uuid]` 直接复用 PRD-0019 引入的 `![img:<uuid>]` 内嵌图片占位符先例（同一份 `RichCommentInput`/`useRichTextInput` 基础设施），按同样的道理和现有 emoji `[name]` 正则共存、互不误吃。

### 与 PRD-0017"吉祥物表情包自定义"的边界

两者在中文表述上容易混淆，但完全不是同一个功能——已在 Out of Scope 明确排除，避免后续实现或 review 时误合并成同一个 ticket。
