# PRD: 用户注销（软删除）

## Problem Statement

用户删除当前是硬删除（`domain/user/repository.go:36` + `useradmin/service.go:Delete`），DB 行直接消失，但内容侧作者信息是**创建时快照**（如 `comment.AuthorName`，`application/comment/service.go:814`）——已删用户的评论照常显示原用户名头像，只有 OAuth 角标消失（`enrichOAuthIdentities` 的 `FindByIDs` 查不到）。结果：

1. 已删用户在评论区/推文仍以正常用户形象出现，语义错乱；
2. 硬删除不可恢复，误删无法补救；
3. email/username/OAuth 绑定随硬删释放，但无审计快照、无撤销余地。

## Solution

删除 = 软删除（注销态），对标 GitHub @ghost / Discord Deleted User 模式：账号不可登录、身份释放可重新注册、内容保留但作者统一显示「已注销用户」占位、后台可筛选可恢复。

### 数据模型

- `users` 加 `deleted_at timestamptz`（NULL=活跃）。用裸 `*time.Time` 列 + 显式查询条件，**不用 `gorm.DeletedAt`** 类型——GORM 的全局软删过滤会吞掉「含已删」的展示查询，而本方案恰恰需要两类查询并存（登录路径排除已删，展示路径包含已删）。仓储层显式控制。
- 身份唯一索引改**部分唯一索引**（migration 手写 DDL）：
  ```sql
  CREATE UNIQUE INDEX uq_users_email ON users(email) WHERE deleted_at IS NULL;
  CREATE UNIQUE INDEX uq_users_username ON users(username) WHERE deleted_at IS NULL;
  CREATE UNIQUE INDEX uq_users_google_id ON users(google_id) WHERE google_id IS NOT NULL AND deleted_at IS NULL;
  CREATE UNIQUE INDEX uq_users_github_id ON users(github_id) WHERE github_id IS NOT NULL AND deleted_at IS NULL;
  ```
  先删原全量唯一索引再建部分索引。原值保留在行内（审计 + 恢复依据）。
- GORM 模型 tag 去掉 `uniqueIndex`（索引由 migration 管，防止将来 AutoMigrate 类工具重建全量索引）。

### 领域行为

`user.User` 加注销状态与不变量：

- 注销用户：不可登录（`CanLogin` 前置）、不可被 OAuth 匹配、不可被找回密码；
- `User.Delete()` 领域方法置 `deletedAt`，应用层编排（吊销 session、吊销全部 PAT、发布 `UserSoftDeleted` 事件）；
- 恢复 = 清 `deleted_at`，前置校验身份占用：email/username/google_id/github_id 任一已被活跃用户占用 → 拒绝（409，提示冲突项）。

### 查询路径分野（核心）

| 路径 | 行为 |
|---|---|
| 登录（identifier 查询）、注册查重（ExistsByEmail/ExistsByUsername）、OAuth 匹配（FindByEmail/FindByGoogleID/FindByGithubID）、admin 列表默认视图 | **排除**已删（显式 `WHERE deleted_at IS NULL`） |
| 内容作者填充（FindByIDs 展示变体）、admin「已注销」筛选、恢复预检 | **包含**已删 |

仓储接口新增/调整：

- `FindByIDsForDisplay(ctx, ids)`：含已删，返回带 `DeletedAt` 感知的实体（聚合根暴露 `IsDeleted()`）；
- 既有 `FindByID/FindByEmail/FindByUsername/FindByIDs/ExistsByEmail/ExistsByUsername` 全部加排除条件。

### 展示占位（统一规则）

身份填充层（评论 enrich、推文作者、文章作者、chat 成员）查到 `IsDeleted()` 用户时，DTO 输出：

- 名字 → `已注销用户`
- 头像 → 空串（前端渲染默认占位头像）
- 无 OAuth 角标、无 GitHub 主页链接、无可跳转主页

评论快照（author_name/avatar_url 存内容行）保留原值用于未删用户（快照语义：改名不影响旧评论）；已删用户的评论在 DTO 层**覆盖快照为占位**——列表查询时按 created_by 批量查含已删用户集合，命中即替换。`reply_to_name`（parent 快照）走同一替换。

### 注销编排（application 层）

`useradmin.Service.Delete` 改软删流程：

1. 守卫不变（root 不可删、不可删自己、被委派超管限制）；
2. `u.Delete()` 置位 + Save；
3. 吊销全部 session（已上线，`fix(useradmin): 删除用户后吊销其全部 session`）；
4. 吊销该用户全部 PAT（`api_tokens` 全删或标记失效——按 PAT 域既有失效路径）；
5. 发布 `UserSoftDeleted` 事件（audit 消费记档）。

### 恢复（管理端）

- `POST /admin/users/{id}/restore`（`user:update` 权限）：预检身份占用 → 冲突 409（body 列出冲突字段）→ 通过则清 deleted_at + Save + 审计；
- 前端 admin.users.tsx 加「已注销」筛选 tab：列表请求带 `status=deleted`，行内灰显 + 恢复按钮。

## 接口契约

### DELETE /admin/users/{id}（语义变更，路径不变）

- 行为：软删除（上述编排）
- 响应：`200 { "message": "用户已注销" }`

### POST /admin/users/{id}/restore

- **鉴权**：`user:update`
- **成功** `200`：恢复后的 AdminUserDTO
- **错误**：不存在/未注销 `404`；身份冲突 `409` `{ "conflicts": ["email", "github_id"] }`；root 参与按既有守卫 `403`

### GET /admin/users（扩展）

- query 加 `status=active|deleted`（缺省 active）

## 安全考虑

- 注销必须同步吊销 session 与 PAT（否则 TTL 内凭证仍有效）。
- 身份释放只动唯一性（部分索引），原值留在行内不公开暴露：任何 DTO 序列化不得输出已删用户的原 email/username/google_id（admin 视图除外，站长审计需要）。
- 恢复的身份占用预检必须覆盖全部四个身份列，防恢复后撞索引 500。

## 测试策略

- 仓储：排除/包含两类查询行为；部分索引下注销后同 email 可注册（集成/迁移测试）。
- 领域：注销用户 CanLogin=false；Delete/Restore 状态往返。
- 编排：注销吊销 session + PAT；恢复冲突 409 列冲突字段；恢复成功往返。
- 展示：已删用户评论 DTO 名字/头像/角标全占位；reply_to_name 占位；未删用户快照不受影响（回归）。
- 登录：注销用户邮箱密码登录 401；OAuth email 匹配不中已删用户（建新号路径）。

## 已确认事项（访谈决策）

1. 注销后内容作者显示占位「已注销用户」（不保留原名快照）。
2. email/username/OAuth 绑定注销即释放，可被新用户注册（部分唯一索引实现）。
3. 恢复能力对标调研结论（GitHub ghost / Discord Restore）：不做固定冷静期，后台随时可恢复，冲突时拒绝并提示。
4. 与 PRD-0033 同分支（feat/auth-account-linking）推进。
