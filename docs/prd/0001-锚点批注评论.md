# PRD-0001：段落划线锚点批注评论

> 状态：ready-for-agent
> 北极星：Medium / GLM 阅读器式的「段落划线锚点评论」——把评论从页面底部的「事不关己区」拉回到正文里，让讨论发生在它指向的句子上。
> 范围：文章详情页（`/blog/$slug`）评论模块的全部重建；前后端协同。
> 适用项目领域词汇：见 `CONTEXT.md`（Owner、Editor、TOC、Announcement Presentation、Authentication 等）。

---

## Problem Statement

作为一个深度长文的读者，我在读到某一段、某一句觉得「这里说错了」「这里我有补充」「这段写得真好」时，唯一的表达通道是滚到页面最底部的评论区，写一条和正文脱离上下文关联的自由评论。结果是：

- 我的评论**丢失了它指向的位置**——作者和其他读者看不到「我在说哪一段」。
- 评论区**积压成一片与正文无关的留言墙**，作者无法快速定位「哪些段落引发了最多讨论」。
- 评论和阅读是**两件事**：阅读在正文区，讨论在底部区，二者割裂。

现有的 `comments` 表已支持嵌套（物化路径 `path` + `depth` 最大 4）和 emoji 反应，但前端**完全没有评论 UI**（`features/comments/{ui,lib}` 是空目录），且后端仍是匿名访客模式、缺少锚点定位字段、缺少「审批中」可见性。换句话说：数据模型有骨架，但既无锚点能力，也无可用 UI。

---

## Solution

为文章详情页引入**双轨制评论**，两轨数据共存于现有 `comments` 表、通过 `anchor` 字段是否为空分流，互不干扰：

1. **选区批注轨（Annotation Track）**——读者选中正文任意连续文本，浮动工具条出现，点击后右侧 sticky 侧边栏展开空白卡片（以选中原文为引言）。提交后，正文该处出现 neon 高亮，与右侧卡片形成「双侧信息层」联动（滚动到高亮↔卡片亮起、点击卡片↔回到高亮）。

2. **底部自由评论轨（Free Comment Track）**——页面底部传统的评论区，`anchor` 为空的顶级评论。承载与正文无强位置关联的总体讨论。

**双轨数据模型**：复用现有 `path + depth` 嵌套结构，`anchor` 只是顶级评论（`depth=0`）的可选属性；回复（`depth≥1`）通过 `path` 前缀天然归属到父评论所在的轨，绝不跨树。

**身份与状态（双轨认证 + 匿名留言板模式）**：两条轨道认证要求不同——

- **底部自由评论轨**：
  - **登录用户**：作者信息从会话用户记录填充，无配额，提交后立即看到自己 pending 评论带「审批中」徽章，看得到所有 approved 评论，可回复/反应。
  - **匿名用户（留言板模式）**：必须填昵称 + 邮箱，并通过**邮箱验证码**两步流提交。匿名是单向留言板，强约束：
    - **黑洞可见性**：匿名 viewer 看不到任何评论（含自己刚提交的），评论区显示「登录后查看 N 条评论」+ 留言入口；提交后 toast「已提交，管理员审核通过后登录可见」。
    - **一篇一次**：同一 `(ip_hash, normalized_email)` 在同一文章下仅能评论一次，二次提交 409。
    - **失效能力**：匿名回复他人、匿名 emoji 反应（看不到对象，逻辑自洽禁用）；登录用户仍可对匿名评论反应/回复。
  - **身份识别**：`anonymous_id = (ip_hash, normalized_email)`，双因子解决 NAT 共享 IP 误伤（不同邮箱 = 不同身份）；`ip_hash = SHA256(middleware.GetClientIP)` 本期接线（之前是半成品）。
- **选区批注轨**：**强制登录**。划线批注是「身份可见的高亮动作」，匿名不允许——既鼓励实名讨论、又便于追溯滥用。后端校验：`POST /comments` 携带 `anchor` 时，`created_by` 必须非空（登录态），否则 401。

**匿名两步流**：
1. `POST /posts/{postId}/comments/code { email }` → 生成 6 位码 → `CodeStore.Store(prefix="comment", email, SHA256(code), TTL 10min)` → Resend 发邮件；限流 `CommentCodeRateLimit`（5/min/IP 防邮件轰炸）。
2. `POST /posts/{postId}/comments { body, author_name, author_email, code }` → `CodeStore.Verify(prefix="comment", email, SHA256(code))`（一次性，Lua 原子，5 次错误锁定）→ 失败 400 → 通过则 per-post 配额校验 → 落库 pending。

提交后默认 `pending`；登录提交者本人立即可见并带「审批中」徽章，他人不可见。文章 Owner（参见 `CONTEXT.md` 的 Owner 词条）的评论以 neon-green 高亮，运行时判定。

**锚点定位**：采用「块内 offset」方案——锚点挂在选区所在的块级元素上（`<p>` / `<h2>` / `<li>` / `<pre>`），`block_id` = 块纯文本的 SHA1 前 8 位（跨渲染稳定、SSR/客户端一致）。持久化五元组 `(block_id, start_offset, end_offset, selected_text, block_text_hash)`；`block_text_hash` 不匹配时进入单块 fuzzy 重定位，全失败则降级为页面级评论（不丢失内容）。

## User Stories

### 阅读与浏览

1. 作为读者，我想在阅读文章时看到正文里已有他人划线高亮的段落，这样我能立即感知「这段引发了讨论」。
2. 作为读者，我想在桌面 2xl+ 屏幕上看到正文右侧有一个常驻的批注侧边栏，集中展示当前文章的所有批注卡片，这样我能一眼看到讨论全貌。
3. 作为读者，我想在正文滚动到某条高亮时，右侧对应的批注卡片自动高亮（neon 边框亮起），这样我能知道「现在这段的讨论是这一张卡」。
4. 作为读者，我想点击右侧批注卡片，让正文自动滚动到对应的高亮位置，这样我能反向定位讨论指向的句子。
5. 作为读者，我想在小屏（lg 以下）设备上没有右侧栏时，点击正文高亮能弹出行内气泡卡片看到批注内容，这样移动端也能消费批注。
6. 作为读者，我想在页面底部看到一个传统的自由评论区，承载与正文无强位置关联的总体讨论，这样两类讨论互不干扰。
7. 作为读者，我想看到每条批注/评论上的 emoji 反应（点赞、喝彩等），这样我能快速感知讨论的情绪倾向。
8. 作为读者，我想看到某条批注下有几个人回复（用 neon-pink 表示「有回复」），这样我能识别「热讨论」与「冷批注」。
9. 作为读者，我想看到文章 Owner（作者本人）的批注/评论以 neon-green 高亮且带「作者」徽章，这样我能快速识别作者亲自下场参与的讨论。

### 划线创建批注

10. 作为已登录读者，我想用鼠标选中正文任意连续文本（同一块内），看到一个浮动工具条出现在选区正上方，这样我能开始一次批注。
11. 作为已登录读者，我想在浮动工具条上点击「划线批注」按钮，右侧栏立即展开一张空白卡片、把选中原文作为引言展示、输入框自动聚焦，这样我能零跳转、所见即所得地写批注。
12. 作为已登录读者，我想在浮动工具条上直接点几个快捷 emoji 给选中段落加反应（不必写文字），这样轻量互动也能被表达。
13. 作为已登录读者，我想在跨块选区时被工具条温柔拒绝（提示「请在同一段落内选择」），这样避免产生无法稳定锚定的批注。
14. 作为已登录读者，我想在未登录状态下选中正文时，浮动工具条的「划线批注」按钮提示我登录，这样匿名用户被引导去登录而不是直接被拒。
14a. 作为匿名访客，我想不登录就能在底部自由评论区留言（填昵称 + 邮箱 + 邮箱验证码即可），这样轻度参与不必注册账号。
14b. 作为匿名访客，我想明白「底部评论可匿名，但划线批注需登录」这条边界，这样我不会在尝试划线时困惑为什么被拦。
14c. 作为匿名访客，我想在填完邮箱后收到一封验证码邮件，输入验证码才能提交留言，这样防止机器人刷留言。
14d. 作为匿名访客，我想知道自己「一篇文章只能留一次言」（提交时如已留过则被拒），这样我不会重复提交。
14e. 作为匿名访客，我提交留言后看到「已提交，管理员审核通过后登录可见」提示，明白我的留言不会立即显示也看不到他人的，这样我理解留言板的单向语义。
14f. 作为匿名访客，我想在评论区看到「登录后查看 N 条评论」的引导而不是裸评论区，这样我有动力登录参与完整讨论。
15. 作为已登录读者，我想在批注提交后立即在右侧栏看到自己的批注（带「审批中」徽章），即使它还没被审核通过，这样我有即时反馈、不会以为提交失败而重复提交。

### 回复与互动

16. 作为已登录读者，我想在右侧批注卡片或底部评论卡片上点击「回复」，输入框就地展开，这样讨论能嵌套展开（最大深度 4，沿用现有 `path + depth` 模型）。
17. 作为已登录读者，我想给某条批注/评论加 emoji 反应，且系统保证幂等（同一人对同一 emoji 只算一次），这样反应数准确不灌水。
18. 作为已登录读者，我想在登录态下撤销自己刚加的 emoji 反应，这样误点能撤回。
19. 作为已登录读者，我想看到嵌套回复以缩进的对话树形式展示（沿用 `AnnouncementCard` 的票据美学：font-mono + neon 色阶 + border-edge-hairline），这样长讨论的层级清晰。

### 审批与状态可见性

20. 作为评论提交者，我想在提交后立即看到自己的 `pending` 评论带「审批中」徽章（仅自己可见），这样我不需要等审核才确认提交成功。
21. 作为评论提交者，我想在别人看不到我的 pending 评论时也不会「以为丢了」——徽章文案明确告诉我「管理员审核通过后公开」，这样我理解流程。
22. 作为读者，我想只看到 `approved` 状态的他人评论，永远看不到他人的 pending/spam/deleted，这样评论区不会被未审核内容污染。

### 管理员审核

23. 作为管理员，我想在后台审核列表里看到新提交的批注和自由评论（标识它是批注还是自由评论、锚定的原文摘录是什么），这样我能快速判断是否通过。
24. 作为管理员，我想批量审核通过/标记垃圾/删除，这样面对大量评论时能高效处理（沿用现有 `BatchUpdateStatus` 接口）。
25. 作为管理员，我想看到一个「待审核数量」角标，这样我不会错过新提交。

### 锚点健壮性

26. 作为作者，我希望文章做了小幅修订（修正错字、调整语序）后，历史批注依然正确指向原位置，这样修订不会摧毁历史讨论。
27. 作为作者，我希望文章大幅重写某段后，落在该段的旧批注能「降级」为页面级评论而不是消失，这样历史内容不会无声丢失。
28. 作为系统，我要在锚点的 `block_text_hash` 与当前块内容不匹配时，用 `selected_text` 在该块内做子串查找重定位；多次命中时用前后 16 字 context 唯一化；全部失败则降级为页面级评论，这样保证锚点的健壮性。

### 开关与配置（预留）

29. 作为作者，我想在文章级别开关「是否允许批注」（默认开），这样某些文章（如纯公告）可以关闭划线、只保留底部评论。
30. 作为站点管理员，我想在站点设置里全局开关批注功能（默认开），这样必要时能全站降级为「只有底部评论区」。
31. 作为读者，我想在批注被关闭的文章上看到正文无高亮、无右侧栏、底部评论区照常，这样关闭是干净的、不残留半成品 UI。

### 可访问性与体验

32. 作为使用键盘的读者，我想用 Tab 能聚焦到正文高亮、用 Enter 打开对应批注卡片，这样键盘也能消费批注。
33. 作为开启 `prefers-reduced-motion` 的读者，我想看到高亮 glow、卡片亮起等动画都被降级为静态，这样不会被动画打扰（沿用 `AnnouncementBar` 的 WCAG 2.2.2 约束）。
34. 作为使用屏幕阅读器的读者，我想高亮和批注卡片有正确的 `aria` 关联（高亮 `aria-describedby` 指向卡片、卡片 `aria-labelledby` 指向高亮），这样辅助技术能正确朗读。
35. 作为读者，我想在批注/评论的加载阶段看到 shimmer skeleton（已有 `shared/ui/shimmer-skeleton`），而不是空白，这样加载体验不突兀。

## Implementation Decisions

### 后端 schema 变更（`comments` 表）

- 新增 anchor 列，**全部 nullable**，仅在顶级评论（`depth=0`）非空：
  - `anchor_block_id` VARCHAR(16) —— SHA1(块纯文本)[:8]
  - `anchor_start_offset` INTEGER
  - `anchor_end_offset` INTEGER
  - `anchor_selected_text` TEXT —— 选中原文（fuzzy 锚）
  - `anchor_block_text_hash` VARCHAR(16) —— 块内容快照（漂移检测）
- 新增 `created_by` UUID REFERENCES users(id) NULLABLE（**保留**匿名 `author_name/email` 模式，登录后填充 `created_by`，匿名评论 `created_by` 为 NULL）；登录用户的 `author_name` / `avatar_url` 从会话用户记录快照（不依赖 user 表存活）。**关键约束**：`anchor` 非空时 `created_by` 必须非空（DB 层 CHECK：`anchor_block_id IS NULL OR created_by IS NOT NULL`），强制批注登录。
- **`ip_hash` 字段接线**（之前是半成品，handler 未填）：本期 handler 必须用 `middleware.GetClientIP(r)` + SHA256 填充 `comments.ip_hash`。这是「一篇一次」匿名配额的硬依赖。
- **per-post 匿名配额索引**：新增索引 `idx_comments_anon_quota (post_id, ip_hash, author_email) WHERE status IN ('pending','approved')`，支撑「同一 `(ip_hash, author_email)` 在同一文章下仅能评论一次」的 O(1) 查询。`author_email` 存储前需归一化（小写 + trim）以保证配额稳定。
- 新增 `is_author` 不持久化（运行时计算，见下）。
- 预留（本期建字段，前端按需读）：`posts.allow_annotations` BOOLEAN DEFAULT true；站点设置新增 `annotations_enabled` BOOLEAN DEFAULT true。
- 不改 `body` 列类型（仍是 TEXT，纯文本 + emoji，沿用 027 迁移哲学）。
- 不引入编辑接口、@提及、富文本、邮件通知（见 Out of Scope）。

### 后端 API 契约变更

- `POST /api/v1/posts/{postId}/comments`：
  - **双轨认证**：底部自由评论轨保留匿名（`author_name` / `author_email` + **邮箱验证码 `code`**）；选区批注轨强制登录（携带 `anchor` 时校验会话 `created_by` 非空，否则 401）。
  - 请求体：匿名时 `author_name` / `author_email` / `code` 必填，`author_url` / `avatar_url` 可选；登录时这些字段从会话用户记录填充（请求体传也以会话为准，防伪造），无需 `code`。
  - 新增可选 anchor 字段（顶级评论才有）：`anchor: { block_id, start_offset, end_offset, selected_text, block_text_hash }`。
  - **匿名提交校验链**：`CodeStore.Verify(prefix="comment", email, SHA256(code))` 失败 → 400「验证码错误或已过期」；通过则继续 → ip_hash 接线 → per-post 配额校验 → 落库 pending。
  - 限流沿用 `CommentRateLimit`（3/min/IP）。
- **新增 `POST /api/v1/posts/{postId}/comments/code { email }`**：匿名评论发码接口。生成 6 位码 → `CodeStore.Store(prefix="comment", email, SHA256(code), TTL 10min)` → Resend 发邮件；限流 `CommentCodeRateLimit`（5/min/IP，防邮件轰炸，与提交限流隔离）。仅匿名需要，登录用户不调。
- `GET /api/v1/posts/{postId}/comments`：
  - **黑洞模式**：匿名 viewer（无会话）返回**空数组** `[]`（看不到任何评论，含自己刚提交的）。
  - 登录 viewer：返回 `approved` 评论 **联合 当前会话用户自己的 `pending` 评论**。
  - 排序仍 `created_at DESC`（顶级）/ `ASC`（回复）。
- `CommentDTO` 新增：`anchor`（同上结构，可为 null）+ `is_author` bool（运行时：`comment.created_by == post.author_id`）+ `status`（让前端能渲染 pending 徽章）。
- 不变：嵌套 `path + depth`、emoji 反应接口（`/comments/{id}/reactions` 三件套 + batch）、管理员审核接口（`/comments/{id}/approve|spam`、`DELETE`、`/admin/comments/*`）。
- pictures 字段：handler 当前未解析（半成品），本期**接线**到 `CreateCommentRequest`，让批注/评论能附图。

### 后端模块边界（DDD，沿用现有 `comment` + `commentreaction` 两聚合）

- `domain/comment/entity.go`：`Comment` 聚合新增 `Anchor` 值对象（含 5 字段 + 校验：`block_id` 非空、`start_offset < end_offset`、`selected_text` 非空、`block_text_hash` 非空）；`NewComment` 接受可选 `Anchor`；**关键校验**：`Anchor != nil` 时 `UserID` 必须非空（强制批注登录），匿名评论 `Anchor` 必须为 nil；`SetParent` 不变。
- `application/comment/service.go`：
  - `CreateInput` 保留匿名 `author_*` + 可选 `UserID`（登录态）+ 可选 `Anchor` + 匿名必填 `Code` + handler 填充的 `IPHash`。
  - 新增 `SendCodeInput { PostID, Email }` command，复用 `appshared.CodeStore`（prefix=`"comment"`）+ 邮件 `EmailSender`（在 comment 包重声明接口，复用 Resend 实现）。
  - `Create` 校验链：登录态跳过验证码；匿名态 `CodeStore.Verify(prefix="comment", email, SHA256(code))` → 失败 `ErrInvalidCode`；通过 → per-post 配额查询（`CountByPostAndAnon(postID, ipHash, email) >= 1` → `ErrAnonQuotaExceeded`）→ 落库。
  - `ListByPost` 改为接受 `viewerUserID`（nullable，匿名 viewer 为 nil **返回空数组**）+ `viewerIPHash` + `viewerEmail`（备用，本期匿名一律返回空，不留特例）；登录 viewer 返回 approved ∪ viewer's pending。
- **基础设施复用**（全部现成）：邮件 `infraemail.Sender`、`appshared.CodeStore`（Redis + 原子 Lua）、`middleware.GetClientIP`、`RateLimit` 工厂；`generateVerificationCode` / `sha256Hash` 从 auth 包提到 `application/shared`（或在 comment 包复制，二者都很短）。

## Out of Scope

明确**不做**，避免范围蔓延：

- **评论编辑接口** —— 当前后端无 PUT/PATCH 编辑 body，本期不补。

- **自动反垃圾**（敏感词、链接黑名单、AI 分类、重复度检测）—— 仅靠人工审核 + 限流。

## Further Notes

### 设计共识来源

本 PRD 综合自一次 `/grill-with-docs` 会话，所有决策点逐条经用户拍板：北极星（段落划线锚点）/ 锚点粒度（纯选区 offset）/ offset 基准（块内）/ block_id（内容哈希）/ 锚点嵌套融合（双轨制 + anchor 只附顶级）/ 容器（右侧侧边栏双侧信息层）/ 高亮形态（neon 下划线+背景，severity 配色）/ 创建流（浮动工具条 + 侧边卡片）/ 富文本（纯文本+emoji）/ 加载（首屏全量预取）/ 作者高亮（运行时判定）/ **身份（双轨认证：底部评论可匿名、划线批注强制登录）/ pending 审批中徽章**（修正自初版「全部登录强制」）/ **匿名留言板模式（黑洞可见性 + 邮箱验证码两步流 + 一篇一次配额 + ip_hash 接线）**（修正自初版「匿名等同登录体验」）/ handler 测试本期建立 / e2e 本期不引入 / PRD 落盘 docs/prd。

### 与现有架构的契合

- **DDD**：完全沿用 `comment` + `commentreaction` 双聚合，无新聚合、无新包；只是实体加字段、service 加参数、handler 改契约。
- **认证**：复用现有 Auth middleware + `middleware.GetUser`，与 `CONTEXT.md` 的 Access Token / SSR 探活词条一致；不引入新认证概念。
- **设计语言**：与 `AnnouncementCard` / `AnnouncementBar` 同构（severity→neon 色、font-mono 票据美学、SpotlightCard 外壳、border-edge-hairline、prefers-reduced-motion 降级、react-bits 动效）。
- **数据获取**：沿用 feature 三件套（keys/queries/mutations）+ `apiGet/apiPost` + `clientQueryClient` 单例 + 详情页 loader 的 `ensureQueryData` 模式。

### 提交与 issue 拆分粒度（指导后续 `/to-issues`）

遵循 AGENTS.md 的提交原子性规范，特别澄清一个易误解点：**「独立组件单独提交」仅适用于公共组件，不是所有组件**。

- **必须单独提交**的：
  - `shared/ui` 下的通用组件（新增、重构、修 bug 都单独）。
  - 被**多个 feature** 引用的实体、接口、hooks、utils（如 `entities/comment`、跨 feature 的算法）。
- **不必单独提交**的：feature 内部的组件。本 PRD 的 `features/comments/ui/*`（`AnnotationLayer` / `AnnotationSidebar` / `AnnotationInlineBubble` / `FloatingToolbar` / `CommentCard` / `CommentForm` / `CommentSection` / `ReactionBar` / `PendingBadge`）属于 `comments` feature 内部，**按职责分组提交**即可（如「批注侧边栏相关组件一组」「底部评论区相关组件一组」），不要每个组件拆一个 commit。
- **feature 内部 lib**（`features/comments/lib/{block-id,range-to-anchor,relocate,severity}.ts`）同理：只服务本 feature，按职责与对应 UI 接入合并提交；只有当某个 lib 被 comments 之外的 feature 引用时才需要单独提交。
- **判断提升时机**：本期默认 YAGNI，不提前把 feature 内部组件抽象到 `shared/ui`。只有当第二个 feature 真的要复用时（如 `PendingBadge` 被公告模块复用），才做 `refactor(web): 将 X 从 features/comments 移动到 shared/ui` 单独提交，再在新 feature 接入。
- 其余仍按 AGENTS.md：前后端分离提交、同层按职责拆分、`fix:` 指向具体对象、重构与功能分离、测试与实现可同组。

### 风险与回退

- **最高风险**：fuzzy 重定位算法——必须用穷尽三路径的单测锁死（见 Testing Decisions）。
- **次高风险**：handler 测试 seam 是全仓首份，定型成本不可忽视；若时间紧张，可把 handler 测试拆成独立 issue（先建 seam 框架 + stub auth helper，再补具体用例）。
- **回退路径**：anchor 列全部 nullable + 双轨通过 anchor 是否为空分流——若批注功能出现严重问题，可通过站点级 `annotations_enabled=false` 开关全站降级为「只有底部评论区」，不丢数据、不需迁移回滚。
