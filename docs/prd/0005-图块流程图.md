# PRD: 图块（流程图 / Diagram Block）接入

## Problem Statement

博客文章正文目前无法插入流程图、时序图等结构化图示。作者要在文章里表达系统架构、调用流程、状态迁移时，只能外链图片或退化为 ASCII 图——前者无法跟随站点明暗主题、源码不可搜索不可复用、升级渲染器要重刷存量，后者表达力有限。CONTEXT.md 与 ADR-0004 早已预留「图块（Diagram Block）」领域概念（通用 `format` 属性节点 + 围栏块 Markdown 载体 + 浏览时渲染 + 渲染器注册表 + 弹层编辑），本期将其落地，首期支持 mermaid 格式。

## Solution

落地图块能力，作为已实现的数学公式功能的同构复刻：新建独立 `diagramBlock` atom 节点（携带 `format` + `source` 属性），编辑器内沿用弹层编辑交互，阅读端走浏览时渲染（content_html 只存语义化标记，不烘焙 SVG）。把阅读端当前写死的 `if (data-type === ...)` 分发升级为真正的 `format → 渲染器` 注册表抽象。针对 mermaid 的 XSS 风险（per-diagram `%%{init}%%` 可绕过全局 strict，见 docmost CVE-2026-23630）采用双重防线，针对主题无法 CSS 跟随的特性采用「主题切换重新 initialize + 重渲染」。

## User Stories

1. 作为文章作者，我想在正文里用 ` ```mermaid ` 围栏块直接写流程图源码，这样不用切到外部工具画图再贴回
2. 作为文章作者，我想通过斜杠菜单（slash menu）插入流程图，这样不记得围栏语法也能上手
3. 作为文章作者，我想点击图块弹出浮层编辑源码并实时看到渲染预览，这样所见即所得地调整图
4. 作为文章作者，我想在弹层里看到 mermaid 语法错误的明确提示，这样能快速定位拼写问题
5. 作为文章作者，我想用 Backspace 或弹层删除按钮移除整个图块，这样能干净地撤销插入
6. 作为文章作者，我写的同一份 mermaid 源在编辑器和阅读端渲染一致，这样不会「编辑器看着对、发布后变了」
7. 作为访客，我想在阅读文章时看到渲染好的流程图（而非 mermaid 源码），这样能直观理解结构
8. 作为访客，当文章作者写错 mermaid 语法时，我想看到友好的「图表渲染失败」降级提示而非整页报错，这样阅读不被中断
9. 作为访客，当我切换站点明暗主题时，流程图的颜色（背景、文字、线条）随之切换，这样暗色模式下不刺眼、不违和
10. 作为访客，在没有 JavaScript 的环境下，我仍能看到 mermaid 源码（可读的文本降级），这样不是一片空白
11. 作为访客，当流程图宽度超出正文栏时，我想能横向滚动查看而非被裁剪，这样不丢失信息
12. 作为访客，我浏览的页面不会被恶意 mermaid 源注入的脚本攻击，这样站点有基本安全保障
13. 作为开发者，我想新增图表格式（如未来的 plantuml）时只需在注册表登记一个渲染器，这样不用改阅读端分发逻辑
14. 作为开发者，我想 mermaid 这类大体积依赖只在文章真含图块时才加载，这样不含图块的文章页不付额外体积代价

## Implementation Decisions

### 节点模型

- 新建独立 TipTap atom 节点 `diagramBlock`（group: block，atom: true），不复用 codeBlock 分流
- 两个属性：`format`（字符串，首期仅 `"mermaid"`，预留多格式）与 `source`（字符串，mermaid 源码）
- atom 节点意味着 source 不进 contentEditable——避免 mermaid 源被自由编辑破坏语法、也避免与公式 `latex` 属性同型的「setNodeMarkup 降级 TextSelection」问题（复用 `update-math-latex` 同事务重建 NodeSelection 的 helper 模式）
- 与 CONTEXT.md「图块」词条（通用 format 属性节点）及 ADR-0004 决策 5 完全一致

### Markdown 载体与输入

- 双入口：` ```mermaid ` 围栏块（参照 codeBlock 的 markdownTokenizer/parseMarkdown/renderMarkdown 钩子机制）+ slash 菜单「插入流程图」命令
- ` ```mermaid ` 经 marked fence 规则解析为 `diagramBlock { format: "mermaid", source: <围栏内容> }`；序列化回写为带 mermaid info string 的围栏块
- 未知 info string 的围栏块仍走原 codeBlock 路径（不劫持）

### content_html 载体（语义化标记）

- 渲染输出：`<div data-type="diagram-block" data-format="mermaid" data-source="<HTML 转义后的源码>">`
- data-source 携带 HTML 转义后的原始源码，阅读端无损提取（避免反解渲染产物）
- 遵循 ADR-0004「content_html 只存语义化标记」：最终 SVG 在读者浏览器渲染，保存时不烘焙

### 编辑交互（弹层编辑）

- 沿用 ADR-0005 的弹层编辑模型：文档内永远只显示渲染结果，点击选中弹出跟随浮层（源码输入 + 实时预览 + 删除按钮）
- 复用数学公式的浮层基础设施：`@floating-ui/dom` absolute 策略 + portal 进编辑器滚动容器 + flip/shift middleware + Esc/外部点击关闭契约
- 面板内容：等宽 textarea（多行）源码输入 + 实时预览区（max-h + overflow-auto）+ 删除按钮
- 实时预览与阅读端共用同一渲染核心（`renderMermaid`），保证「写作所见 = 发布所渲染」
- 首期不做 mermaid 语法补全（收益低、命令空间大）

### 阅读端渲染管线

- content_html 经现有 hast 白名单管线解析 → 识别 `div[data-type="diagram-block"]` → 挂 ref 容器
- 组件内：动态 `import('mermaid')` → `mermaid.render(id, source)` 拿 SVG 字符串 → DOMPurify 二次清理 → 写入 ref 容器 innerHTML
- `startOnLoad: false` 禁用 mermaid 自动扫描，全部由组件显式驱动
- 不把 mermaid SVG 走 hast sanitize 白名单（SVG 子集太复杂，白名单要么过宽要么漏放）；改由 DOMPurify 在 ref 写入前清理，与 hast 管线各专其职

### 安全防线（双重）

- **第一道**：全局 `mermaid.initialize({ securityLevel: "strict" })`，挡住大部分常规注入
- **第二道**：render 产出的 SVG 经 DOMPurify 清理（`USE_PROFILES: { svg: true, svgFilters: true }`，强制剥 `on*` 事件属性、`<script>`、`foreignObject` 里的可执行内容）
- 必要性：mermaid 支持 per-diagram `%%{init: { "securityLevel": "loose" }%%` 指令，单图能覆盖全局 strict（docmost CVE-2026-23630 / GHSA-r4hj-mc62-jmwj 的攻击路径）。第二道 DOMPurify 兜底
- 这是本 PRD 的安全命门，必须有测试覆盖 XSS payload 被清理

### 主题策略

- mermaid 把颜色烘焙进 SVG，渲染后无法用 CSS 改主题（ADR-0004「浏览时渲染」决策的理由之一）——切主题必须重新 `initialize({ theme })` + 对每个图重新 `render`
- 用 mermaid 内置 `base` 主题 + `themeVariables` 定制：
  - **框架对齐站点明暗**：`background` / `primaryTextColor` / `lineColor` / `primaryBorderColor` 等从站点 CSS 变量（oklch 格式）读取并转换为 mermaid 要求的 hex
  - **节点保留彩色**：`primaryColor` / `secondaryColor` / `tertiaryColor` 保留 mermaid 默认彩色，保证流程图节点间可区分（站点是 neutral 灰度，全对齐会让节点难辨）
- 组件持有 source（来自 data-source），监听站点主题变化（`next-themes` resolvedTheme 或 `<html>.classList` 的 MutationObserver），主题变 → 重新 initialize + 重渲染所有可见图块
- oklch→hex 转换：`getComputedStyle` 读 CSS 变量值，转 hex 喂给 mermaid（mermaid themeVariables 只认 hex）

### 渲染器注册表

- 新建注册表抽象，把当前散落在 `markdownComponents`（span/div/pre/code 四个 if 分支）的分发逻辑收敛
- 形态：`{ [format: string]: { ReaderComponent: React.LazyExoticComponent, sanitizeAttrs: string[] } }`
- 首期注册 `mermaid` 一项；新增格式（plantuml 等）是纯增量登记，不动分发代码
- 同步收敛 hast sanitize schema：图块新增的 `data-format` / `data-source` 属性加入白名单

### 懒加载

- mermaid 组件用 `React.lazy` 动态 import，仅在文章真含 diagram-block 节点时 Suspense 触发拉取
- CSS（若有）随异步 chunk 拆分，不进主包
- 沿用数学公式（katex-element lazy）/ shiki / CodeRunner 的同款懒加载模式

### 容器与降级

- 阅读端图块容器：居中 + `overflow-x-auto`（流程图常宽屏，横向滚动而非缩放变形）
- 错误降级：mermaid 语法错误时，阅读端显示「图表渲染失败」占位 + 折叠的源码（不向读者暴露详细错误）；编辑弹层内联显示具体错误（便于作者修）
- 无 JS 环境：data-source 作为文本内容降级显示（mermaid 源本身可读）

### 组件边界

| 模块 | 位置 | 职责 |
|------|------|------|
| 渲染核心 | `shared/ui/diagram/` | `renderMermaid(source, theme)` 纯函数（含 DOMPurify）、`getThemeVariables(isDark)` 纯函数 |
| 渲染器注册表 | `shared/ui/diagram/` | `format → 渲染器` 映射，收敛阅读端分发 |
| 阅读端组件 | `shared/ui/diagram/` | lazy 组件，source → ref 容器 → SVG |
| 编辑器节点 + NodeView | `features/editor/` | diagramBlock schema、围栏往返、弹层 NodeView |
| hast 白名单 | `shared/markdown-preview/` | 追加 data-format/data-source 放行 |

## Testing Decisions

### 测试原则

- 只测外部行为，不测实现细节
- 纯逻辑抽离到最高 seam 测（不依赖 DOM 的部分），集成层靠手动验证
- 前端组件测试用 `@testing-library/react` + `vitest`

### 测试 Seam（3 个）

| Seam | 层级 | 覆盖 |
|------|------|------|
| `renderMermaid(source, theme)` 纯函数单测 | shared/ui 纯函数 | mock `mermaid.render` 返回固定 SVG，**真实测 DOMPurify 清理**：合法源 → 产出 SVG；语法错 → 抛错；**XSS payload（`%%{init:{securityLevel:loose}%%` + `<img src=x onerror=...>` + `<script>`）→ on*/script 被剥除** |
| `getThemeVariables(isDark)` 纯函数单测 | shared/ui 纯函数 | isDark=true → 暗色 themeVariables；false → 亮色；节点填色保留默认（不被覆盖） |
| hast sanitize 白名单 | 复用现有 HtmlContent.test.tsx | 含 `div[data-type=diagram-block][data-format][data-source]` 的 HTML → 属性被白名单保留 |

### 不测（沿用数学公式先例，靠手动验证）

- 编辑器 diagramBlock 节点 schema、Markdown 围栏往返（数学公式实现里也无此单测）
- DiagramBlock 阅读端组件集成（mermaid 在 jsdom 异步 + DOM mock 较脆，性价比低）
- 弹层 NodeView 交互（手动验证：开闭、定位、删除）

### 先例

- 纯函数 seam：参考 `shared/ui/katex/__tests__/katex-core.test.ts`
- hast 白名单 seam：参考 `shared/markdown-preview/__tests__/HtmlContent.test.tsx`

## Out of Scope

- **复制源码 / 导出 SVG / 点击放大**：首期纯核心链路，这些读者侧附加交互后续迭代
- **mermaid 语法补全**：弹层源码输入首期无补全（命令空间大、收益低）
- **多图表格式（plantuml / graphviz / d3 等）**：首期只 mermaid，但注册表抽象为后续纯增量登记预留
- **mermaid 交互（点击节点跳转 / 高亮）**：首期只静态渲染
- **站点主题 token 联动配置化**：首期 oklch→hex 映射硬编码，不做成可配置（YAGNI）
- **服务端渲染 / SSR 预渲染 SVG**：与 ADR-0004「浏览时渲染」决策一致，不烘焙

## Further Notes

### 决策来源

- 领域概念与架构大方向：CONTEXT.md「图块（Diagram Block）」词条、ADR-0004 决策 5（图块预留同模型）
- 弹层编辑交互：ADR-0005（已取代 ADR-0004 原写的「双态编辑」）
- 1:1 参照系：已实现的数学公式功能（编辑器 `MathView` 瘦适配器 + `MathPopoverView` 弹层 + `shared/ui/katex` 共享渲染核心 + `markdown-components` lazy 分发）

### 安全研究锚点

- docmost CVE-2026-23630 / GHSA-r4hj-mc62-jmwj（2026-01）：per-diagram `%%{init}%%` 覆盖 securityLevel + `dangerouslySetInnerHTML` 无清理 → 存储型 XSS。本 PRD 的双重防线即针对此攻击路径
- mermaid 官方安全文档：默认有 baseline DOMPurify，但 baseline config 历史上有洞（CVE-2025-54881 同类）。第二道 DOMPurify 用显式 profile 兜底

### 主题研究锚点

- mermaid 把颜色烘焙进 SVG，渲染后无法 CSS 改主题（herczeg 2025-01 实践 + mermaid 官方 theming 文档）——切主题必须重新 initialize + 重渲染
- 站点主题 token 为 oklch 格式（shadcn neutral 调色板，`web/src/styles.css`），mermaid themeVariables 只认 hex，需 oklch→hex 转换层

### 待新增 ADR

落地时建议新增 **ADR-0007（图块安全与主题策略）**，记录两个有取舍的决策：(1) 双重 XSS 防线（为什么不只靠 strict）；(2) base + themeVariables 的「框架对齐明暗 + 节点保色」策略（为什么不全灰度、为什么不自定义所有变量）。这两点是有长期影响的设计决策，值得 ADR 留痕。

### 已否决（grill 阶段）

- 复用 codeBlock 按 language 分流：与「通用 format 属性节点、预留多格式」的既定架构相悖
- 首期只 mermaid 不建注册表：继续欠债，下次加格式时分发代码堆 5 个分支
- mermaid SVG 走 hast 白名单：SVG 子集复杂，白名单要么过宽（形同虚设）要么漏放（渲染残缺）
- 仅全局 strict 不加 DOMPurify：已被 docmost CVE 证明可被 per-diagram 指令绕过
- 全对齐站点灰度：流程图节点难区分，可读性下降
