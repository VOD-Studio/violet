# PRD: 操作日志模块重构（audit 从装饰品到全站审计基础设施）

## Problem Statement

操作日志（audit）模块已搭好 DDD 四层骨架（`domain/audit` → `application/audit` → `infrastructure/persistence/gorm` → `interfaces/http/handler/audit`），建了 `audit_logs` 表、后台查询页（`/admin/logs`）、`log:view` 权限。但这个模块**实质上不起作用**——后台审计页能看到的只有「管理员增删改了几个用户」，而一个博客系统最该审计的「谁发了文章、谁删了评论、谁改了角色/权限、谁改了站点设置、谁登过系统」**一条都没记录**。

问题分四个维度：

### 1. 覆盖面：全站只有 useradmin 一个模块接入审计

`auditSvc` / `AuditLogger` 的全部调用方仅存在于 `application/useradmin/service.go`（7 处）。已写好路由但**零审计**的模块：

| 模块 | 路由位置 | 应审计操作 |
|---|---|---|
| 角色/权限管理 | `admin_router.go:91-103` | CreateRole / UpdateRole / DeleteRole / UpdateRolePermissions |
| 公告管理 | `admin_router.go:113+` | 公告 CRUD |
| 文章状态 | post service | Publish / UpdateStatus（unpublish/archive） |
| 站点设置 | admin settings | 各组设置 PUT |
| 登录/登出 | auth handler | login/logout（迁移注释列了这两个动作，代码从未调用） |

### 2. 记录内容：缺审计最核心的「变更内容」

行业共识审计日志五要素：实体 + 事件类型 + 时间 + 操作人 + **变更内容(before/after)**。前四项有，第五项基本缺失：

- `Log()`（`audit/service.go:24`）无变更内容，只有 action/resource/id/ip。
- `LogWithDetail()` 有 detail，但全是手工拼的零散字段（`{"role":"admin"}`），**不是 before→after 对比**。
- `update` 操作的 detail 直接传 `nil`（`useradmin/service.go:223`）——「更新了用户」这条日志没有任何变更信息，看了等于没看。
- `resource_name`（用户名/文章标题快照）在 entity 和 PO 都定义了，但 `AuditStore.Append`（`audit_store.go:40-43`）**根本没映射**，永远写空。
- `user_agent` 参数接口签名留着（`useradmin/service.go:24`），函数体 `_ = ua` 丢弃（PO 无对应列，注释「待补」一直没补）。

### 3. 可靠性：写入失败被静默吞掉

所有调用都是 `_ = s.auditSvc.LogWithDetail(...)`。审计写库失败 → 零感知、零降级日志。审计的安全原则是 **fail-safe**（宁可报错/降级也别丢记录），这里是 **fail-silent**——给人「已记录」的错觉，比不记更危险。

### 4. 架构割裂：有 EventBus 死代码却不用

`domain/shared/event.go` 定义了完整的领域事件接口（`DomainEvent` + `BaseEvent`），注释明写「写审计日志」是核心用途之一。但 `application/shared/eventbus.go` 的 EventBus **仅有 `NoopEventBus`**（`Publish` 即丢弃），**无 Subscribe 注册机制**。结果：审计靠 `useradmin` 手工注入 `AuditLogger` 接口、在 service 里逐行手写。覆盖面完全取决于「哪个 service 作者记得注入」——这正是大面积遗漏的根因。`role/command` 的 `CreateRoleHandler` 已注入 EventBus 但发到 noop，等于没发；`UpdateRoleHandler`/`DeleteRoleHandler` 连注入都没做。

## Solution

把 audit 从「贴在 useradmin 上的装饰品」升级为**全站统一的事件驱动审计基础设施**。分三步，对应三批 issue：

**第一步（P0）：让现有审计真正可用**
- 补全写入内容：`Append` 映射 `ResourceName`；`update` 类操作 detail 传 before/after 而非 nil；`Log`/`LogWithDetail` 增加 `resourceName` 参数。
- 改 fail-safe：审计 service 层注入 logger，写入失败时记结构化降级日志（含完整事件快照），不再 fail-silent。
- 接入所有该审计的模块：role/permission CRUD、announcement CRUD、post 状态变更、auth login/logout。

**第二步（P1）：数据层对齐**
- migration：`detail` 列 TEXT → jsonb；补 `user_agent` 列（不再丢弃 ua 参数）；`user_name` 冗余快照在写入时填充（用户删除后仍可追溯）。
- PO 与 migration 对齐。

**第三步（P1）：EventBus 发布-订阅改造**
- 实现真正的 EventBus（Subscribe 注册 + Publish 分发），审计作为统一订阅者消费领域事件。
- 聚合根在状态变更时 `RecordEvent`，应用层事务提交后发布，EventBus 分发给审计订阅者写库——取代逐模块手工注入 `AuditLogger`。

## User Stories

1. 作为站长，我想在后台审计页看到「谁发布了/取消发布了哪篇文章」，这样能追踪内容发布的操作人。
2. 作为站长，我想看到「谁创建/修改/删除了角色、谁改了权限分配」，这样权限变更可追溯（安全审计核心）。
3. 作为站长，我想看到「谁创建/修改/删除了公告」，这样前台公告变更可追溯。
4. 作为站长，我想看到「谁登录/登出了系统、从哪个 IP」，这样能发现异常登录。
5. 作为站长，审计日志的 `update` 操作要带 before→after 变更内容，而不是空 detail——这样我才知道「更新了用户」到底改了什么。
6. 作为站长，审计日志的 resource 要带资源名称（用户名/文章标题），这样不用再去查 ID 对应谁。
7. 作为站长，审计写入失败时我要能在系统日志里看到降级告警，而不是无声丢失记录。
8. 作为开发者，我想审计覆盖面由领域事件统一驱动（聚合根发事件 → 审计订阅），而不是靠每个 service 作者记得手工注入——这样新增功能时审计自动覆盖。

## Implementation Decisions

### 写入内容补全（Issue-0001）

domain entity 已有 `ResourceName` / `UserName` 字段，但 `AuditStore.Append` 不映射 `ResourceName`。修复：

- `Append` 补 `ResourceName` 映射（`audit_store.go:40-43` 当前只映射 Action/Resource/ResourceID/IPAddress）。
- `Service.Log` / `LogWithDetail` 增加 `resourceName string` 参数，透传到 entity。
- `AuditLogger` 接口（`useradmin/service.go:23`）同步加参数。
- `update` 类操作的 detail 从 `nil` 改为传 before/after（`useradmin/service.go:223` 先改，其余模块接入时遵循）。

### fail-safe 可靠性（Issue-0002）

审计 service 层注入 `zerolog.Logger`：

- `Log` / `LogWithDetail` 写库失败时，记 `log.Error()` 降级日志，字段含完整事件快照（action/resource/resourceID/userID/ip/detail）。
- 调用方继续 `_ =`（审计失败不阻断业务请求），但 service 层保证可观测——fail-safe 而非 fail-silent。
- 不把审计写入放进业务事务（避免事务回滚连审计一起丢）；事务后异步写。

### 覆盖面接入（Issue-0003 ~ 0006）

每个模块按现有模式接入 `AuditLogger`（P0 阶段手工注入，P1 EventBus 改造后由订阅者统一接管）：

| Issue | 模块 | service 位置 | 审计操作 |
|---|---|---|---|
| 0003 | 角色/权限 | `role/command` + `permission/command` | CreateRole/UpdateRole/DeleteRole/UpdateRolePermissions |
| 0004 | 公告 | `announcement/service.go` | CRUD（Create/Update/Delete） |
| 0005 | 文章状态 | `post/service.go` | Publish + UpdateStatus（含 unpublish/archive） |
| 0006 | 登录/登出 | `auth/command/*.go` | Login/Logout/GithubLogin/GoogleLogin |

各模块 service 注入 `AuditLogger`（或直接 `*appaudit.Service`），在状态变更后调用 `LogWithDetail`，传 before/after detail + resourceName。角色/权限模块 `CreateRoleHandler` 已注入 EventBus（发到 noop），P0 阶段先手工加 AuditLogger，P1 EventBus 改造后该事件自动路由到审计订阅者。

### 数据层对齐（Issue-0007）

migration 031：

```sql
ALTER TABLE audit_logs ALTER COLUMN detail TYPE JSONB USING detail::jsonb;
ALTER TABLE audit_logs ADD COLUMN user_agent VARCHAR(255);
```

- `detail` 从 TEXT 改 jsonb（PO 已标 `gorm:"type:jsonb"`，migration 落齐）。
- 补 `user_agent` 列，`Append` 映射 ua（删除 service 里 `_ = ua` 的丢弃逻辑）。
- `user_name` 冗余快照：`Append` 写入时填充（从 ctx 取当前用户名或调用方传入），不再只靠查询时 JOIN——用户删除后仍可追溯。

### EventBus 发布-订阅改造（Issue-0008）

当前 `EventBus` 接口只有 `Publish(ctx, []DomainEvent) error`，唯一实现 `NoopEventBus` 直接丢弃。改造：

1. **EventBus 接口加 `Subscribe`**：注册 `func(ctx, DomainEvent) error` 类型的订阅者，按 `EventName()` 路由。
2. **实现真正的 EventBus**（`infrastructure` 层）：内存版同步分发（MVP），Publish 遍历匹配的订阅者调用。后续可演进为异步队列。
3. **审计订阅者**（`application/audit/subscriber.go`）：订阅所有审计相关事件（`user.*` / `post.*` / `role.*` / `announcement.*` / `auth.*`），转换为 `AuditLog` 写库。
4. **聚合根 `RecordEvent`**：`domain/post`、`domain/role` 等聚合根在状态变更方法（`Publish()`/`Unpublish()`/`Archive()`）里 `RecordEvent`。
5. **应用层发布**：各 command handler / service 在事务提交后调 `bus.Publish(ctx, agg.PullEvents())`。
6. **装配**：`app` 层注册审计订阅者到 EventBus。

改造后 P0 阶段手工注入的 `AuditLogger` 调用可逐步移除（由事件驱动替代），但 P0 手工注入保留作为过渡，确保 EventBus 改造期间审计不中断。

## Testing Decisions

- **audit service 层**：fakeStore 模式（已有 `service_test.go`）。覆盖内容补全（resourceName 透传）、fail-safe（注入失败返回 error 时验证降级日志被调用）。
- **audit store 层**：SQLite 临时库（已有 `audit_store_test.go`）。覆盖 ResourceName 持久化、user_agent 列、user_name 冗余写入。
- **各模块接入**：各模块现有测试模式。验证审计调用被触发（mock AuditLogger 断言调用次数 + 参数）。
- **EventBus**：内存实现测试。覆盖 Subscribe 注册、Publish 按 EventName 路由、订阅者错误不影响其他订阅者。
- 不测：PG jsonb 语义、zerolog 输出格式。

## Out of Scope

- **append-only 不可变约束**（PG 触发器禁 UPDATE/DELETE）：P2，依赖 EventBus 改造稳定后做。
- **受控 action 词表枚举化**（编译期约束 create/update/delete/publish/...）：P2。
- **审计日志保留期 + 冷数据归档**：P2（Harness 指出近期热数据留快存储，冷数据归档）。
- **审计搜索 API + webhook 事件流**：P2（Design for API，schema 预留但本 PRD 不实现）。
- **站点设置 PUT 接入审计**：设置模块改动面大且零散，待设置模块稳定后单独立项。
- **评论审核/删除接入审计**：评论审核已有独立后台流程，审计需求优先级低于角色/权限/发布，留后续。

### 难逆决策

- **EventBus 同步分发 MVP**：先做内存同步版，不引入消息队列（YAGNI）。异步队列待性能需求驱动。
- **P0 手工注入与 P1 事件驱动并存**：EventBus 改造期间，已手工注入的 AuditLogger 保留，避免审计中断；改造完成后逐步移除手工调用。不做大爆炸式切换。
- **detail 用 jsonb 而非 TEXT**：jsonb 支持结构化查询（如查「role 被改成 admin 的所有操作」），TEXT 不行。
- **审计写入在事务外**：业务事务回滚不应丢审计记录（记录「有人尝试了 X 操作」）。代价是事务回滚时审计多记一条失败操作——对审计场景可接受（fail-safe 倾向多记）。

- **领域事件驱动审计**：项目自有 `domain/shared/event.go` 已定义 DomainEvent，注释明写「写审计日志」用途——本 PRD 把这个死设计激活。
