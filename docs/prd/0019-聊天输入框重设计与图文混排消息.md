# PRD: 聊天输入框重设计与图文混排消息

## Problem Statement

聊天界面底部输入框（`MessageComposer`）宽屏下两侧留白过大、整体偏矮，视觉上不好看；同时图片预览与文字输入区之间隔着一条分隔线、各占独立背景，编辑时"选图"和"打字"像两个割裂的面板，而不是一次连贯的输入过程。更进一步，发一张图配一句话时，对方会收到两条分开的消息（图片消息 + 文本消息），不符合用户对"图文合一"的预期。

## Solution

`MessageComposer`（`web/src/features/chat/ui/ChatWorkspace.tsx`）与消息列表容器同步放宽最大宽度，输入框整体加高、加大内边距。共享组件 `RichCommentInput`（`web/src/features/comments/ui/RichCommentInput.tsx` + `useRichTextInput` hook）新增图片行内插入能力：图片作为行内节点插入到光标所在位置，与文字混排、可退格整体删除，机制上镜像现有 emoji 内嵌实现。默认（非 chat）场景下的图片缩略图行去掉分隔线与独立背景，与文字区合并为一张卡片。chat 场景进一步放开发送语义：`domain/chat` 的图片消息允许携带说明文字（caption），单图+文字合并发一条消息；多图仍各自一条消息，说明文字跟随最后一张图片。comments/tweets 的提交模型不变。

## User Stories

1. 作为聊天用户，我想输入框在宽屏下不再两侧留白过大，这样界面更饱满好看
2. 作为聊天用户，我想输入框整体更高一些，这样打字时不会觉得局促
3. 作为聊天用户，我想图片预览区和文字框之间不再有一条突兀的分隔线，这样整个输入区域看起来是一体的
4. 作为聊天用户，我想选好图片后图片直接出现在我打字的位置，而不是掉到文字下面单独一行，这样编辑体验和打字连贯
5. 作为聊天用户，我想插入的图片可以用退格键像删文字一样整体删掉，这样撤销误操作很自然
6. 作为聊天用户，我想图片上传中能在原位看到进度，这样知道还没传完
7. 作为聊天用户，我想上传失败的图片能在原位看到失败状态并可以移除重来
8. 作为聊天用户，我想发一张图配一句话时，对方看到的是一条消息（图+文字合一），而不是两条分开的消息
9. 作为聊天用户，我想一次发多张图片时仍然像现在一样各自一条消息展示，但最后一张图能带上我的文字说明，这样多图场景也不会丢失说明文字
10. 作为聊天用户，我想只发文字不带图片时，行为和现在完全一样
11. 作为聊天用户，我想图文合一的消息也能被引用回复、加表情反应，和普通消息规则一致
12. 作为聊天用户，我想历史消息的展示不受这次改动影响
13. 作为评论/推文用户，我想我的图片输入体验（图片预览行去掉分隔线以外）不受这次改动影响，因为提交模型和 chat 不一样
14. 作为开发者，我想样式改动（宽度/高度/合并缩略图行）可以独立先实现验证，不必等图文混排功能一起上线

## Implementation Decisions

### 输入框视觉重设计（全量：composer + 消息列表）

- `ChatWorkspace.tsx` 中消息列表容器与 `MessageComposer` 容器的 `mx-auto max-w-3xl`（768px）同步放宽为 `max-w-4xl`（896px），两者保持对齐，避免输入框比消息列表更宽/更窄造成的错位。
- `MessageComposer` 外层容器内边距从 `p-3 md:p-4` 加大为 `p-4 md:p-5`。
- 输入区（`RichCommentInput` 的 `inputClassName`）从 `min-h-12 max-h-36 py-2.5 px-3` 调整为 `min-h-14 max-h-56 py-3.5 px-4`，单行高度与内边距更舒适，多行上限从 144px 提到 224px。
- 发送按钮从 `h-7` 调整为 `h-8`，与更高的输入区视觉配平。
- `rounded-2xl` 圆角、`border-input/70` 边框、neon-cyan 聚焦态维持不变——已经和站内其它卡片（消息气泡、侧边栏卡片）的圆角语言一致，不需要为了"好看"额外加大或改变圆角风格。

### 图片缩略图行的默认合并样式（`RichCommentInput` 全量生效）

- `RichCommentInput` 中图片缩略图行（`imageItems.length > 0` 渲染的那一段）去掉 `border-t border-edge-hairline` 分隔线与独立背景色，与上方 contentEditable 输入区视觉合并为同一张卡片。此项对 comments/tweets/chat 全部生效，纯样式改动、不改变任何交互或数据流。
- 该渲染路径是"未开启行内嵌入"时的缩略图展示方式；chat 开启行内嵌入后不会触发这段渲染（见下一节）。

### 图片行内嵌入编辑体验（`RichCommentInput` 新增能力，仅 chat 消费）

- `RichCommentInput` 新增可选 prop `inlineImages?: boolean`（默认 `false`）。comments（`CommentForm`/`FloatingToolbar`）与 tweets（`TweetCommentForm`）不传，行为和样式完全不变。chat 的 `MessageComposer` 传 `inlineImages={true}`。
- `useRichTextInput` 新增 `insertImage(id, url, status)` 方法，机制镜像现有 `insertEmoji`：用 Selection/Range API 在光标处插入一个 `<img data-image="<id>">` 行内节点，可随文字换行、退格整体删除。
- 上传流程与现有 `uploadFilesList` 保持一致（`useChunkedUpload`），差异在插入位置：`inlineImages=true` 时，选中文件后立即在光标处插入一个带 `data-image-status="uploading"` 的占位节点（叠加进度展示），上传成功后原地把节点替换为最终 `data-image` 节点（真实 URL），失败则原地替换为错误态节点、点击可移除；不再进入独立的缩略图行渲染路径。
- `value`（markdown 字符串）新增图片占位语法，形如 `![img:<uuid>]`，与现有 emoji `[name]` 占位符（正则 `\[([^\]]+)\]`）区分：图片占位符带 `!` 前缀，`markdownToHtml`/`htmlToMarkdown` 需要在现有 emoji 正则之外新增一套图片占位符正则，优先于 emoji 正则处理，避免互相吃字符。
- `onImagesChange` 回调保持现有 `PictureInput[]` 结构；数组顺序即为图片在文字流中的插入顺序，不需要额外的位置字段。

### chat 发送语义调整（仅 chat；comments/tweets 不受影响）

- `domain/chat`：`NewImageMessage` 新增可选 `content` 参数（caption），放开"图片消息 `content` 必须为空"的既有不变量，允许二者共存；`content` 非空时同样受 `MaxMessageContentLength` 校验，逾长报错。
- `application/chat` `Service.SendMessage`：`case domainchat.MessageImage` 分支把 `in.SendMessageInput.Content` 透传给 `NewImageMessage`（此前该分支忽略 content）。
- `interfaces/http/handler/chat`：请求体已含 `content` 与 `media_id` 字段，image 类型请求不再需要忽略 `content`，直接透传给应用层。
- 前端 `MessageComposer.sendMessage()`（`ChatWorkspace.tsx`）：现有"每张图各发一条 image 消息，最后再发一条 text 消息"的循环调整为——发送本轮最后一张图片时把文字说明一并带上（这条消息同时含 `media` 与 `content`）；只有本轮完全没有图片、只有文字时，才单独发一条纯文本消息。引用回复（`reply_to_id`）仍附着在本轮首条发出的消息上，规则不变。
- 前端消息气泡（`ChatWorkspace.tsx` 消息渲染）：`message.type === "image"` 分支在图片下方新增 caption 展示——`message.content` 非空时用现有 `ChatMessageContent` 组件渲染在图片卡片内，视觉上另起一行、不与既有的图片元数据 footer（体积/尺寸）混在一起。

### CONTEXT.md

- "图片消息（Image Message）"术语已更新，补充"可选携带说明文字（caption），与图片同属一条消息，不再要求图片消息 content 必须为空；多图仍各自一条独立消息，说明文字只跟随最后一张图片"的规则说明。

## Testing Decisions

### 测试原则

- 只测外部行为，不测实现细节；样式改动（宽度/高度/合并缊略图行分隔线）属于纯 CSS class 调整，不新增测试，用户已声明本次 UI 改动不使用浏览器自动化验证，改完由用户自行手动验证。

## Out of Scope

- **一条消息携带多张图片（相册/媒体组）**：现有"多图各发一条独立消息"的行为保持不变，只有文字说明会跟随最后一张图片合并发送。未来若要支持"一条消息多图"，需要把 `MediaID` 单值改造成数组，涉及后端表结构、DTO、前端展示网格、WebSocket 事件 payload 等大改，属于后续独立 ticket。
- **图片粘贴/拖拽直接内嵌**：粘贴仍强制纯文本，拖拽未支持；图片仍只能通过工具栏按钮选择，本期只改变"选中后的插入位置"，不新增触发方式。
- **comments/tweets 接入图片行内嵌入与图文合一发送**：`inlineImages` prop 只 chat 消费；评论/推文继续用现有"文字+独立图片行"的编辑与提交模型，`Comment` 领域模型已支持 `body+pictures[]` 共存，无需改动。
- **历史消息回填 caption**：仅影响新发送的消息，历史图片消息 `content` 为空字符串，不做数据迁移。
- **移动端 contentEditable 图片内嵌的专项适配**：沿用 PRD-0003"移动端 contentEditable 兼容性本期不做专项优化"的既有决定。

## Further Notes

### 与 PRD-0003 的关系

`RichCommentInput`/`useRichTextInput` 由 PRD-0003（评论富文本输入）引入，emoji 内嵌机制（`data-emoji` + `[name]` 占位符 + Selection/Range 插入）是本次图片内嵌的直接参照对象。图片占位符选用 `![img:<uuid>]`（带 `!` 前缀）而非复用 `[name]` 语法，是为了避免和 emoji 的 `EMOJI_PATTERN`（`\[([^\]]+)\]`）正则冲突——两套占位符必须能在同一段 `value` 文本里共存、互不误吃。

### 领域模型现状核对

- `comment`/`tweet` 领域的 `Comment` 实体已有 `body string` + `pictures []Picture`，图文本就共存，不受本次改动影响。
- `chat` 领域的 `Message` 实体是三者中唯一 text/image 互斥的（`content` 与 `mediaID` 不共存），这也是"图文合一"只需要改 chat 一处后端的原因。
- 前端 `ChatMessage`/`MessageDTO` 类型层面 `content?`/`media?` 本就都是可选字段，并未强制互斥，只是后端 switch 分支和 chat 自己的发送循环把两者拆开发送；本次改动不需要新增字段。
