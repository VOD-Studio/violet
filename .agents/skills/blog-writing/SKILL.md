# Blog Writing

根据用户提供的材料、源码、调研或工程会话写博客文章，让读者能独立理解；只需记住一个短经验时写笔记。选题围绕一个值得解释的问题，不围绕“这次做完了什么”。用户只要求维护本 skill 时，不生成或入库会话内容。

## 先确认本次交付

| 用户意图 | 本次交付 |
|---|---|
| 自动会话收尾 | 轻量筛选有价值的发现；没有就沉默，有则提供明确选题及可审阅稿，不默认写入博客 |
| 写文章、沉淀经验 | 完整稿件；已有明确题目和范围时直接沿用 |
| 改稿 | 读取指定原文，修正用户指出的问题；不默认扩大为整篇重写 |
| 存草稿、发布、更新指定文章 | 完成相应稿件后按已获授权执行博客操作 |
| 发布已完成的现稿 | 核对稿件、目标和授权，进入出版参考；不重新选题或擅自重写 |

“写文章”授权写作，“存草稿”授权保存，“发布”授权公开。已明确的授权持续有效，不反复确认；缺少授权时交付可阅读稿件。草稿仍是远端写入。

## 选题：先找到值得解释的发现

从材料中找一个具体读者的问题，以及这次工程实践能提供的回答。需要更细的判断时读 [decision-guide.md](references/decision-guide.md)。

- **文章**：问题需要一条展开的解释，例如一个反直觉行为如何发生、一个选择在什么条件下成立、一次故障如何被证据定位。证据足以支撑这条主线。
- **笔记**：一个明确触发条件和修法已足够帮助未来检索，扩写只会重复。短小但非显然的修复也有价值。
- **更新已有内容**：本次只增加旧主题的新边界、反例或证据，优先补原文。
- **不写**：只有实现清单、过程状态、通用常识或已记录过的结论。

完成一个功能、改了很多文件、通过很多测试都不是选题理由。自动捕获不追求覆盖本次所有改动，围绕最有解释价值的主题展开，其余材料可不收录。用户显式要求文章时遵守其交付形式；材料缺口就针对性补读或说明，不自行降级成笔记。

写作前围绕候选主题查重：文章用 `search_posts`，笔记用 `list_notes` 并检查分页；只读可能相关的正文。MCP 不可用时仍可完成本地写作，说明尚未查重；不要猜测已有文章或创建新远端内容。

## 写作：交付一条读者跟得上的解释

新写文章或实质重写时读 [article-workflow.md](references/article-workflow.md)。保留一个简短写作约定：**谁的问题 → 本文回答 → 支撑回答的关键材料**。它用于约束取舍，不做正文模板。

- 让具体情境、状态变化、原因与结果连接起来；重要结论应让读者看到它如何成立。
- 按解释需要自由使用 Markdown 的标题、列表、表格、引用、脚注、链接、图片、公式与代码；流程、状态或跨组件时序适合时用图，不设字数或形式配额。引用文章或论文时核对原文，将出处放在论点附近或脚注中。写法参考见 [markdown.md](references/markdown.md)，不因当前站点解析能力排除合适的语法。
- 区分实际观察、源码确认和条件推演；复用已有证据，只补影响解释的缺口，不为写作另开工程验收。
- 笔记写清触发场景、非显然结论及可复用动作，不强行展开为小论文。
- 中文正文保留稳定技术术语；不虚构第一人称经历、测量数字、失败场景或验证结果。

完成初稿后独立审读，具体指出缺上下文、跳过因果、无依据结论与可删除旁枝；按发现改稿。复杂文章可用独立 agent，若不可用则单独进行编辑审读，不能用作者自评分代替问题定位。

稿件可供用户完整审阅：按请求展示正文或提供本地 Markdown 链接。标题、摘要与标签不能替代正文。用户只要求写作时，到这里即可交付，不启动出版流程。

## 保存或发布

有相应请求时读 [publishing.md](references/publishing.md)，按实际 MCP 能力定位目标、保存、回读、发布与确认。文章用 `violet-posts`，笔记用 `violet-notes`；不绕过它们直接写 HTTP 或数据库。

远端写入前执行敏感扫描及语义检查。真实秘密必须删除；未公开的草稿也不能容纳凭据。扫描只证明命中检查通过，不能证明文章有价值或可读。

尚未获得保存/发布授权时，先交付具体稿件，再集中询问目标操作；无应答就保持本地稿。已授权就执行，不重复要求用户裁定。失败保留同一稿件、已知目标 ID 与最后确认阶段，恢复时先核对远端状态，不盲目重新创建或重写文章。

收尾报告稿件入口或博客链接、实际状态与 ID。分别说清写完、已保存与已发布，不能用其中一种冒充另一种。
