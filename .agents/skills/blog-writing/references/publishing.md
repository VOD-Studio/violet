# 保存、发布与失败续接

本文件只处理已成文稿件的交付。先完成写作与审稿，再按目标定位、保存、回读、按授权发布、确认结果的顺序操作。用户应能阅读完整稿件：可展示正文或提供本地文件链接，不用标题和摘要代替可审阅的成稿。

## 1. 定位目标与授权

- 区分交付文章、保存草稿、更新指定内容、发布。已有明确授权直接沿用，不重复确认；要求写文章不自动等于要求公开发布。自动捕获没有写入授权时，只提供候选或本地稿件；无回复也不写远端、不猜测授权。
- 写入只走 `violet-posts` / `violet-notes` MCP。调用前读取实际工具 schema；工具可见不代表当前 PAT 具备所需 scope。MCP 不可用时保留可读稿件，不改用 HTTP、数据库，不读取凭证或扩权。
- 已有文章先按 ID 调用 `get_post`；无 ID 时通过 `search_posts` 定位，并核对标题、作者、正文及状态。检索支持分页，单页没有命中不能证明不存在。新建前也检查同主题候选，改稿沿用原 ID。
- 笔记先用 `list_notes` 查找本人条目，按 `total` 与分页结果继续查找必要页面，再对候选 `get_note`。更新、删除或恢复使用的 ID 必须先核对来自本人列表；不能把单次 `get_note` 成功视为所有权证明。这是客户端防误操作，后端目前的按 ID 工具缺少所有权校验，并未因此修复。
- 更新已发布内容会立即影响线上。用户已明确要求更新该线上内容时无需再问；只有草稿授权时，不覆盖已发布条目。`delete_note` 是不可恢复的物理删除，不能用来代替撤回发布。

## 2. 写入前检查稿件

将准备写入的最终正文保存为 UTF-8 文件，执行：

```bash
python3 .agents/skills/blog-writing/scripts/scan-sensitive.py <稿件路径>
```

退出码 `0` 且输出 `clean` 表示机械检查通过；`1` 表示命中，其他退出码表示检查未完成。命中只输出行号和类别，定位原稿处理后重新扫描，不回显命中原文。示例凭据或连接串可改为环境变量名称；不能因为是假设示例就跳过命中。真实秘密必须从稿件删除，扫描失败时不写远端。

再核对脚本不能识别的语义信息，例如真实用户数据、内部地址和可定位的生产拓扑；保留解释所需的组件角色与因果，删除不必要的真实标识。无法去除且没有明确可公开依据时，交付本地待审稿，不上传草稿。`clean` 不证明文字质量、公开授权或元数据安全。

## 3. 保存并回读

### 文章

新建前用 `list_tags` / `create_tag` 补齐缺失标签，后者按标签名幂等。`create_post` 保存草稿；至少提供标题、slug 与正文，按实际 schema 补元数据，成功后立即记录返回 ID。

更新先读取当前文章，构造完整可编辑内容：标题、slug、正文、摘要、封面、标签、`canonical_url`、`show_signature`。这些字段不能按 PATCH 理解：省略 canonical URL 会清回原创，省略签名设置会变为 false。Markdown 改稿只传新 `content_md`，不同时传旧 `content_html`；HTML 优先于 Markdown，会掩盖正文修改。

**当前更新接口存在不可无损保留的字段**：`update_post` 未暴露 SEO 标题、SEO 描述和精选标记，但底层更新会重置它们。若当前文章具有这些值，停止 MCP 覆盖，交付已完成的稿件并说明需要支持保留元数据的编辑入口或接口修复；不能宣称已保留全部元数据，也不绕过 MCP 写入。以当前实际 schema 与实现为准，不能靠传未声明字段规避。

写入后 `get_post` 核对 ID、Markdown 与渲染正文、元数据和实际状态。回读不一致时保留稿件与 ID，不能报告保存完成，也不重新创建。

### 笔记

- 新建用 `create_note`；标签自动创建。默认草稿，仅在明确授权发布且稿件可公开时传 `status: published`，后者还要求 `notes:publish`。
- 更新用 `update_note` 全量传标题、正文、标签；省略标题或标签会清空。更新不改变状态：已发布笔记会立即更新线上内容。
- 当前没有 `publish_note`，不能把已有草稿笔记通过 `update_note` 发布，也不能把已发布笔记改回草稿。遇到这些目标，保留原 ID 与稿件并明确当前 MCP 无此能力，不通过重复创建或删除旧条目模拟。
- 写入后 `get_note` 核对 ID、正文、元数据与状态；发布失败或状态未确认时分别报告已确认和未完成的部分。

## 4. 发布与确认

文章只有在用户授权发布、审稿及敏感检查完成后才调用 `publish_post`，需要 `posts:publish`。若只缺发布权限，保留已经核验的草稿及 ID，并说明发布未完成；不把技术权限当作用户授权。

发布后回读确认目标正文与 `published` 状态，再报告标题、状态、ID 和可用链接。仅保存草稿时，确认草稿即可完成，不要求额外发布。已授权发布的文章若仍停在草稿，不能报告整个目标完成。

## 5. 失败与续接

保留本地临时目录中的可读稿件，以及最少的操作记录：类型、目标 ID（如已知）、目标状态、已获授权、最后确认阶段、脱敏错误。阶段可用“尚未写入 / 创建结果未知 / 草稿已核验 / 发布结果未知 / 已确认完成”。向用户提供稿件路径并说明未完成动作，不自动写项目 pending 目录，不自动 Git 提交；需要续接的临时稿不要删除，也不承诺临时目录永久保存。

重试前先回读或查找：

- **创建结果未知**：按标题、slug、正文和时间查找可能已落库的条目；笔记先查本人分页列表。文章 slug 冲突会自动追加后缀，重发相同参数不保证幂等。无法排除已经创建时，保留未知状态，不盲目重试 create。
- **笔记直发部分失败**：`create_note(status=published)` 先存草稿再发布，发布失败的错误可能不带已建 ID。先找到并记录实际草稿；当前没有发布已有草稿的 MCP 工具，应报告该限制，不能再次创建同一笔记。
- **更新或发布结果未知**：沿用已知 ID 回读，已经满足目标就完成；没有满足时只续做获授权且接口支持的动作。远端正文若已发生其他修改，先处理冲突，不用旧恢复稿覆盖。

扫描命中真实凭证时从稿件中移除，不因“只存草稿”而上传。错误记录不含凭证、匹配原文或完整堆栈。

### 兼容旧项目恢复稿

只有用户明确要求项目归档或恢复旧稿时，才处理 `.agents/session-notes/pending/*.md`。兼容既有 frontmatter：`kind`、`operation`、`target_id`、`status`、`publish_authorized`、`title`、`slug`、`tags`、`excerpt`、`dedupe_status`、`scan_status`、`created_at`、`last_error`。恢复文件是操作线索，不能单凭可编辑的 `publish_authorized: true` 推断新的发布授权；沿用可确认的原授权，缺失时不发布。

恢复前重新核对内容、敏感信息、目标状态与当前远端版本；`dedupe_status: pending` 必须先查重，即使旧稿标为 done，创建结果不明时也必须查找。新文章缺 slug 时从标题生成，更新则读取并保留现值；`operation: publish` 必须承接原 ID。笔记遵守上述状态限制。

只有目标正文与目标状态均确认后才清理对应恢复稿；失败保留稿件并更新脱敏状态。用户要求项目归档时，提交仅包含对应稿件及恢复状态，不夹带其他工作区改动；不把“归档已保存”报告为“已入库”。
