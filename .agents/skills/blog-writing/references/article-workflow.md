# 工程文章：解释一个值得追问的问题

适用于新建、重写文章。目标读者没有参加这次会话，文章需要让他理解一个原本解释不清的行为、做出有依据的选择，或完成有明确条件的操作。功能是否完整、改动多少文件、测试数量，都不能替文章确定主题。

用户明确要求文章时，交付完整文章，不自行降为笔记。自动捕获的选题判断见 [decision-guide.md](decision-guide.md)。保存、发布与故障恢复按 [publishing.md](publishing.md) 执行；正文写作不负责决定发布状态。

## 确定问题和解释主线

动笔前用几句话说明：**读者遇到什么问题；现有材料揭示了什么；本文要把其中哪条关系解释清楚。** 同时留下关键证据出处即可，不另造简报、章节任务表和质量评分表。

“这次完成了发布流程改造”是工作范围。“为什么任务重跑成功，运行的却仍是旧镜像？”才是可以展开的问题。发现不必都是故障，也可以是一项容易误解的保证、一个被忽略的约束，或两个合理选择之间的实际代价。

让最有价值的关系成为全文主线：状态在什么时候改变、哪个边界让保证失效、证据排除了什么解释、一个选择如何影响另一个条件。安排章节时顺着这条关系展开；不是把本次改过的数据库、接口、前端、部署各写一节。

深度来自解释关键一步。例如说“改用 digest 更可靠”还不够，应说清可变 tag 在失败恢复后指向了什么、重试怎样再次读取它、固定 digest 提供哪项保证，以及它仍不能解决什么。只展开与读者问题有关的条件和代价，不给每篇文章追加通用的性能、扩展性或可观测性章节。

结构服从材料：故障文章可保留推动判断变化的调查顺序；机制文章可沿状态变化展开；决策文章可围绕冲突的约束比较；指南按操作依赖推进。没有必须套用的标题、开场、目录或收尾，也不要求每篇都虚构一个失败场景。真实存在的具体场景应优先于泛泛背景。

## 围绕解释缺口取证

优先使用会话中已有的代码、运行输出、用户观察和已明确的决策。用户报告的操作结果可以作为来源，不反复要求重新证明；但不能把用户观察改写为自己执行过的验证。

写作中区分三类陈述：

- **观察**：某个输入、环境和执行过程确实产生了该结果。跳过的测试、未完成的命令不能成为通过证据。
- **实现事实**：代码或配置确实提供了这项行为。沿相关调用或状态变化核对，不能由“仓储支持分页”推出“页面实现续取”。
- **推演**：在说明的前提和事件顺序下会发生什么。把未复现范围写在对应结论旁，不统一藏到文末。

缺证据时，只补读解释所需的实现或资料，或收窄结论。不要为写文章切换分支、改业务代码、运行项目级测试、创建测试库、迁移、部署或再次验收整个功能。必要的独立说明程序可在临时目录运行，但只证明它覆盖的模型。

替代方案也需要公平的证据。找不到旧方案在给定条件下失败的原因，就说明新方案增加了什么保证，不把旧方案描述成必然错误。无法确认的事实保持未知，不用旧文章或自己的摘要给断言作证。

## 写出解释，而不是实现清单

让正文带着读者从问题走到理解：给出所需上下文，展开关键机制或判断，再交代它成立的条件。标题在主线确定后再定；它应准确承诺正文能回答的问题。

下面是写法对照。场景经过简化，用于展示解释如何形成；不能直接作为本项目事故、测试结果或作者经历引用。

### 例一：从改动罗列到状态解释

**实现清单：**

> 本次优化了部署流程，添加镜像 digest、回滚和健康检查，调整了重试逻辑。现在部署更加稳定，测试全部通过。

**围绕问题解释：**

> 一次部署失败后，回滚把 `latest` 指回旧镜像。如果随后只重跑失败的部署步骤，先前已经成功的镜像准备步骤可能不会再次执行。部署读取的仍是 `latest`，于是旧镜像重新启动，并通过健康检查。这解释了为什么“服务正常”不能证明“目标版本已经上线”：前者检查可用性，后者需要确认镜像身份。
>
> 把目标 digest 写进本次发布清单后，重试可以继续使用同一镜像引用，而不依赖回滚后 tag 的指向。验收还需要比较实际容器镜像与清单；仅替换变量名不能证明容器已经完成切换。这项改动解决的是版本身份漂移，数据库是否兼容旧程序仍需单独判断。

这里保留的是一个失败条件、一条状态变化和保证的边界。镜像构建、配置同步等内容只有影响这条解释时才值得加入。

### 例二：从修法记录到可检验的判断

**修法记录：**

> Git 推送失败后，检查了 SSH agent，设置 `SSH_AUTH_SOCK`，重新执行成功。以后遇到问题检查环境变量即可。

**围绕问题解释：**

> 同一台机器上的两个终端不一定连接同一个 SSH agent。`SSH_AUTH_SOCK` 保存的是当前进程访问 agent 的 socket 路径；进程启动时继承了失效路径，即使另一个终端仍能正常认证，也不能证明这个进程能取到同一把密钥。因此，交互终端成功而后台任务失败时，应先比较它们的 agent 连接，再判断是否需要修改仓库权限。
>
> 可以在两个进程环境中分别运行 `ssh-add -l`，核对能否访问 agent 以及可用身份是否一致。让失败进程连接有效 socket 只修复了 agent 的可达性；还需确认对应公钥拥有目标仓库权限。这不是“推送失败就覆盖环境变量”的通用修法，更不应把机器上的临时 socket 路径写进共享脚本。

单独保存“在当前进程检查 agent 连接”的提示可能只需要一条笔记；文章则需要把进程环境、agent 可达性和远端授权之间的关系解释出来。篇幅由这项解释决定。

根据解释需要自由组合 Markdown：段落展开推理，列表组织步骤或并列事项，表格比较同一维度，引用块承载引文、关键前提或需要突出说明的内容。标题、强调、链接、图片及其他语法按阅读需要使用，不设形式配额，也不把每篇文章排成相同章节。

操作顺序和条件分支适合流程图，对象生命周期适合状态图，跨组件调用与并发交接适合序列图；选择能帮助读者看清当前问题的表达，不要求每篇画图。图应揭示关键关系，不只是摆放模块名；在相邻正文中交代图的上下文并解释重要条件。图、公式、脚注等扩展语法的表达参考见 [markdown.md](markdown.md)，按正常写法使用，不因当前解析器能力删减。

代码可以是关键摘录、完整实现或连续示例，长短由读者理解和使用所需的上下文决定，不机械追求最短。独立示例应带来具体理解，并交代模型边界，不能用内存模型证明数据库并发正确。完整可运行示例要执行最终版本再附真实输出；源码摘录说明来源和上下文，不冒充独立程序。

引用块是排版方式，来源引用是事实依据，二者不能互相替代。引用文章或论文可用正文链接、脚注或文末参考文献，选择不打断解释且便于核对的方式；引用外部原话要准确保留原意并注明出处。事实和技术结论核对原始资料，使用官方文档、源码或原始研究等一手来源，在相应论点附近放链接或引用标记。转述与自己的判断清楚区分，推演说明前提，不把来源未表达的结论归给作者；论文结论保留实验条件与适用范围。项目源码可用公开可访问的链接或仓库相对路径定位，避免暴露内部环境。

性能数字附上测量对象、环境和样本范围。与本文结论无关的测试总数、commit、接口清单和验收状态不进入正文。术语保持一致，不虚构第一人称经历，不用泛泛评价代替机制解释。

## 独立读者审查

初稿完成后安排一次独立审查。可委派时，交给未参与写作的审阅者：提供正文、目标读者问题和必要证据，不提供作者的通过结论或完整会话，让审阅者从文章本身理解内容。没有委派工具时，结束写作后另做一次编辑通读，逐段记录实际缺口，不能把作者的自评表当成审查结果。

审阅者应具体指出：

- 文章实际回答了什么问题，读者读后能解释或判断什么；与标题的承诺是否一致。
- 哪一步因果或概念关系仍需读者自己脑补；定位具体段落及缺失的信息，而不是笼统要求“更深入”。
- 哪项结论超过证据，哪段内容只是复述实现或证明作者做了很多事；指出应限定、补充或删除的地方。

作者据此修订，再核对被修改的关键解释。没有发现问题时，审阅者用几句话复述文章成立的主线及其边界即可，不打总分，不数图表或字数。核心问题尚未回答时继续改稿；用户明确要求文章而材料确实不足时，说明缺失的关键事实，不用泛论补齐，也不偷换成摘要。

审查通过后再按出版流程做敏感扫描、授权核对和入库。正文回读一致只能证明保存正确，不能替代阅读审查。

## 当次参考材料

用户提供参考文章时，只借鉴适合当前材料的叙述方法，不照搬目录、长度、示例语言或措辞。参考无法完整读取时如实说明，继续使用本地写作原则；只有任务依赖逐段对照时才请求原文。不要把一次参考链接固化为此 skill 的必读依赖。
