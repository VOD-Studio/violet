# 选题、文章与笔记的判断

自动捕获时按本文件筛选；用户已明确要求文章、指定题目或要求改稿时，保留其交付目标，只用这里的方法聚焦材料，不擅自降级。文章写作见 [article-workflow.md](article-workflow.md)。

## 从发现筛选，不从完成清单分级

先找这次成果里值得解释的发现：什么行为和直觉不同，哪个约束改变了选择，什么证据揭示了真正原因。为有价值的候选说明**读者会遇到的问题、能够解释的发现、支持它的证据**。若三者无法连成一条关系，不必列为候选。

优先选择解释价值最强、证据足够且已有内容尚未讲清的主题，不默认覆盖整个会话。涉及一个配置项的改动可能足以形成机制文章；完成一个大功能也可能只有实现清单，不值得自动写文章。

例如一次发布流程改造同时调整构建、重试和静态资源：

- “本次如何完成 CI/CD 优化”仍是任务范围，不能直接当选题。
- “为什么重试成功却没有运行目标版本”有具体问题；若材料能展开回滚、可变引用和版本验收的关系，可以成为文章。
- “某个工具的布尔输入必须按布尔值判断”若只有一个明确陷阱与修法，适合笔记。
- 格式化、例行测试通过和无新增发现的重复修复不单独沉淀。

自动捕获不设文章或笔记配额；没有足够价值可以不写，也不要把同一主题同时包装成文章和笔记。多个候选确实独立时分别判断，不能只因牵涉不同文件就拆开。

## 选择最合适的去处

| 材料能带来什么 | 处理方式 |
|---|---|
| 回答一个具体读者问题，需要解释机制、因果、取舍或操作条件；关键关系有证据支撑 | 写文章，围绕这一问题组织材料 |
| 提供一个可独立检索的触发条件、判断或修法，不需要更大的解释背景 | 写笔记，保留同一因果链 |
| 给已有主题增加新触发条件、纠正旧结论或补充关键证据 | 优先形成原文的更新稿，而非新建近义内容 |
| 只有进度、完成状态、重复结论或尚无法确认的猜测 | 自动捕获时不写 |

文章和笔记的区别是读者需要怎样的解释，不是字数长短、改动规模或“功能级”标签。比如 agent 的 socket 检查可以是一条提示；若材料揭示了交互终端与后台进程为何使用不同身份，并能解释何时检查进程环境、何时检查远端权限，则可能值得写成文章。

用户要求文章而证据不足时，先做支持该问题的针对性补读；仍缺核心事实就明确指出缺口，不用笔记或工作总结替代。未知不等于错误，未复现的因果推演可在明确前提和边界后保留。

## 更新与拆分

调用入口规定的只读检索工具核对相近主题。查重比较的是读者问题与结论，不只是标题或 tags；已有文章包含相同解释时，只有新增事实或边界才值得更新。更新已发布内容仍遵守出版流程的授权边界，自动选题不授权覆盖线上正文。

一条笔记应能补全：“遇到这个触发条件时，它能帮助我做出这个判断或动作。”例如，“交互终端认证成功、后台任务认证失败时，先检查二者能否连接预期 agent”，具有清晰的检索入口；“今天终于修好了 SSH”没有。

同一故障的现象、根因、修法和验证保留在一起。仅当两个知识点有不同触发场景、能独立使用时才拆分；读者必须来回拼接才能理解的碎片不算独立主题。

## 语义脱敏

保留组件角色、因果和可复用步骤；移除真实标识。机械扫描 `clean` 不代表语义安全。

应脱敏：

- `ssh root@prod-01.internal` → `连接生产服务器`。
- `/Users/alice/company/private-service` → `本地项目目录` 或仓库相对路径。
- 真实客户邮箱、订单数量和内部实例名 → `测试用户`、`某次真实业务流量`、`生产数据库实例`。

无需因语义而脱敏：

- 公开仓库中的相对路径，如 `web/src/features/posts/`。
- 框架名、标准协议、错误类型和无法映射真实系统的虚构示例。
- `example.com` 这类保留示例域名；若脚本仍命中，按出版流程处理，不自行豁免。

错误做法：

- 只用 `***` 遮住密码，却保留真实用户名、主机和端口。
- 保留 token 前后各四位用于辨认。
- 脱敏成“某处有问题”，使知识失去技术意义；此时标明缺口，按出版流程处理未解决的敏感内容。

扫描、敏感内容的处理和入库权限统一见 [publishing.md](publishing.md)，不在选题阶段推断发布授权。
