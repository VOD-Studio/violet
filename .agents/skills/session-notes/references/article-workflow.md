# 工程文章：让结构服从材料

文章的新建、重写和恢复入库都必须执行本流程。目标是让没有参加会话的读者获得明确收益：理解一种机制、判断一个取舍、复盘一次故障、复现实验结果，或安全完成一项操作。文章不是交差摘要、PR 说明、文件导览或扩写版笔记。

写作简报、证据表、结构方案和审查意见属于内部工作稿，不复制进正文，也不默认写入仓库。用户要求文章时不能只交中间产物。`draft` 只是未公开的存储状态，正文仍须完整、准确、可独立阅读；能否发布按入口文件中的用户授权、质量检查和 MCP 权限共同决定。

## 1. 判断材料适合写成什么

动笔前写一张简短的内部写作简报：

| 项目 | 必须说清的内容 |
|---|---|
| 读者 | 谁会读，已掌握什么，缺少什么 |
| 收益 | 读完能理解、判断、复现或执行什么 |
| 材料类型 | 机制、决策、故障、实验、操作流程，或其他明确类型 |
| 核心材料 | 哪些事实、证据和细节真正产生上述收益 |
| 边界 | 同一会话还做了什么，但与本文关系不足 |

结构由材料决定。下列只是常见组织逻辑，不是模板清单，也不要求逐项覆盖：

- 机制解析可沿请求、对象或状态变化展开，让概念在需要时出现。
- 故障复盘可保留症状、假设、证据转折、根因、修复和回归证明，重点是实际诊断路径。
- 架构或设计决策可从约束与冲突出发，比较可行方案，说明决定、代价和适用条件。
- 实验或调研可围绕问题、方法、观察、解释和限制组织，保留足以判断结论的条件。
- 操作指南可先说明目标、风险与前置条件，再给可执行步骤、检查点和回滚路径。
- 功能实现记录可按用户旅程、领域规则、跨层交接或最难的实现约束组织，不必覆盖每个文件。

一篇文章应有一种占主导的组织逻辑，也可以按材料自然混合。混合的理由来自内容，例如故障复盘在定位根因后需要解释底层机制；不能为了“全面”把六种形式各写一节。

先确定收益和结构，再定标题。自动捕获的材料不够支撑文章时，回到笔记分诊。用户指定完整文章或明确列出内容时，不私自删减其范围；先用现有材料完成可写部分，针对缺失的核心事实取证或说明缺口，不用泛论凑齐。

## 2. 按论点取证，不为写作另开工程任务

优先复用会话中仍然有效的代码、用户观察、运行输出和决策。合并、换分支等由用户说明的状态直接采纳；只有相关实现确已改变时，才针对变化补读。不要重新确认用户已经报告的故障或操作结果。

为关键论点保留简短的 `结论 → 证据出处 → 适用范围` 对照：

- **运行行为**：记录执行的场景、环境、输入和观察。跳过的测试、中断的命令和别处的通过记录都不是本次通过。
- **实现事实**：定位实际调用链、事务对象、约束或配置。仓储支持分页不等于页面会续取；后端幂等不等于客户端重试沿用同一个键。
- **推演**：写明前提、事件顺序和后果，并在对应结论旁注明尚未复现。不把推演统一藏进文末免责声明。
- **未知**：暂不作结论。旧摘要或旧文章只能提供查找线索，不能给自己的断言作证。

补读只围绕解释缺口展开。禁止为写文章切换或新建分支、改业务代码、运行项目级测试、建测试数据库、迁移、部署或再次验收整项功能；这些需要另一个明确工程任务。必要的最小说明程序可以在临时目录运行，且只证明它实际覆盖的模型。材料缺少端到端证据时收窄表述，不为凑“验证章节”扩张任务。

比较方案时要验证逻辑，不能因为当前方案更好，就把旧方案写成必然错误。构造不出真实反例或找不到实现差异时，改写为当前方案实际提供的保证，不替它虚构对手。

## 3. 选择结构，再写全文

按选定的组织逻辑安排内容，不按文件、提交、接口或工具执行顺序。每个准备保留的章节先写清三件事：

`本节在全文中的任务 → 支撑它的具体材料 → 它与相邻章节的关系`

这是规划字段，不是正文小标题模板。不同文章应产生不同结构：故障复盘可以保留调查时间线，决策文需要并列比较，操作指南则首先服从执行顺序和安全检查。

结构审查必须回答：

- 开头是否用适合本文类型的方式建立阅读上下文？故障文可以从症状开始，决策文先交代约束，指南先说明目标、风险和前置条件，实验文说明问题与方法。
- 重要概念第一次出现时是否已有足够上下文？是否只解释后文真正用到的部分？
- 相邻主章节为什么按这个顺序出现？可任意换序的并列内容是否真的都值得保留？
- 最有价值的材料是否得到足够展开，还是被接口表、默认值、文件清单或通用背景挤掉？
- 文章结束时是否兑现写作简报中的读者收益？

结构不过关就重排或删材料，禁止先写几千字再靠连接词粘合。修订旧稿时同样先重建结构；用户说“没有章法”不能用扩写、换标题或逐句润色应付。

## 4. 正文用解释推进，不用清单填满

正文按选定结构推进。机制文解释状态如何变化，复盘文保留证据如何排除假设，决策文把约束与代价讲清，指南让步骤和检查点可执行。不要逐个复述所有 handler、DTO 和配置默认值，也不要把一种写法强套给所有题材。

图表和代码按理解需要选择，没有配额：

- **表格**用于比较同一维度的差异或区分容易混淆的语义。连续几节只有表格加结论，说明解释被省掉了。
- **图**用于表达正文难以口述的边界、交接或并发顺序。节点应揭示关系，不只是把模块名装进方框；图前说明看什么，图后解释它暴露的约束。
- **源码摘录**只保留支撑论点的逻辑，交代输入和上下文；不要为“可复制”贴整份迁移、服务或脚手架。
- **独立示例**必须让读者观察到一个不直观的结果或反例。内存 mutex/map 去重不能证明 PostgreSQL 并发正确，普通 HMAC 验签教程也不能替代真实系统边界的解释。没有这样的理解增量就不加示例。

完整示例应短且自包含，说明它模拟什么、不模拟什么；语言由问题和项目决定，不统一塞 Go。执行的必须是准备入库的最终代码，改过一行就不能沿用旧输出。只有完整运行才贴“实际输出”；未运行的结果不得装成运行记录。按项目真实的代码块格式标记可运行性。

证据尽量放在它支持的结论附近。性能数字必须带输入规模、环境、测量对象和样本范围；本机热请求的毫秒数不能证明生产体验。与本文读者收益无关的测试总数、响应字节、commit 和 PR 状态不要堆成验收周报。确需集中说明验证范围时只保留与正文结论有关的行为及缺口。

## 5. 审稿是质量门禁，不是自评打分

初稿完成后切换为目标读者视角通读。逐项给出具体通过依据或需要修改的段落，不用总分、字数、图表数或“扫描 clean”代替判断。

| 门禁 | 通过条件 | 不通过时做什么 |
|---|---|---|
| 收益兑现 | 标题、开头、正文重心和收束共同兑现写作简报承诺的理解、判断、复现或操作收益 | 调整选题、承诺或正文重心，不只改标题 |
| 结构适配 | 组织方式符合材料类型；章节有明确任务和关系，不是默认模板或模块清单 | 改用更合适的组织逻辑，重排、合并或删除章节 |
| 证据约束 | 关键结论有可定位依据；观察、源码事实和推演没有越界，替代方案没有被无依据地否定 | 补针对性证据、限定结论或删除断言 |
| 材料取舍 | 每段、每图、每段代码都产生承诺的读者收益；删除会损失具体理解或可执行性 | 删旁枝、重复概念、泛用示例和无关验收数字 |
| 表达与完整性 | 非会话参与者能读懂，术语稳定，内容足以独立成立；没有流水账、虚构经历或占位内容 | 回写正文；结构问题不能交给文风润色解决 |

任一门禁失败先改稿，再复核受影响的论证；禁止带着“待扩写”“后续补充”等核心缺口入库。能确认的剩余限制应跟随相关机制解释触发条件和后果，不为显得深刻追加一串缓存、扩展性、可观测性愿望清单。

结构通过后，再做表达检查：

- 用具体对象、动作和结果说清机制，删掉重复预告、空泛评价和会话过程旁白。
- 同一概念保持同一名称；段落承担解释，列表只承载确实并列的事项，不为版式整齐改变技术分类。
- 第一人称只用于材料中真实存在的判断和经历，不编造“我一开始以为”，不靠添加情绪制造作者感。
- 收束方式服从文章类型：机制文可落到适用边界，复盘文落到修复与防复发条件，决策文落到选择及代价，实验文落到观察与限制，指南落到完成检查和回滚入口。不重复目录、不追加口号。

质量通过后才进入 `SKILL.md` 的敏感扫描、授权和 MCP 入库。正文回读或哈希一致只证明存储正确，不证明文章好读；不得用它替代本节审稿。

## 参考材料只做当次校准

本流程的写作简报、结构选择、证据与审稿标准全部保存在本地文件中，执行不依赖某篇外站文章或另一份写作 skill。

用户当次提供参考文章时，可读取并提炼其中与当前材料相容的写法。不照搬措辞、目录、长度、图表数或示例语言，也不把该 URL 固化成本 skill 的必读前置。

参考链接已删除、不可访问或只能读到片段时，明确未取得完整参考，继续根据现有材料执行本地规则；不反复探测、不假称已对齐、不用臆测补原文。只有用户明确要求逐段对照且缺少原文时，才请求提供文本。

从参考材料得到的观察必须改写成适用条件明确的本地原则。某篇机制解析使用行为疑问开场，不代表故障复盘、决策记录或操作指南也必须这样写；原文消失不应影响已经内化的规则使用。
